# 作品集敘事策略 — 架構型專案怎麼被看見

> **狀態**：2026-08-29 建立。起因：投遞時卡在 HR／外行關卡，架構深度沒機會被技術面試官看到。
> **定位**：本檔記錄「怎麼講」，不是「做什麼」。它**不是**任何規格真相，不影響 `docs/00–NN` 的工程契約。
> **正式契約**：架構以 `docs/01-design-doc.md`／`docs/02-dev-spec.md`／`docs/ADR/` 為準。
> **使用方式**：寫任何一段作品集文案、錄任何一支 demo 之前，先查 §3 的翻譯表與 §4 的讀者分層。

---

## 1. 核心診斷：為什麼「做得好」反而看不見

把原本打算展示的五項擺在一起，會看到一個共同結構：

| 打算展示的 | 外行實際看到的 |
| --- | --- |
| Walk／Run／Sprint 平滑切換 | 「角色在走路」 |
| Stop 依腳相自然銜接 | 「角色停下來了」 |
| Jump／Roll／Punch 即時中斷 | 「按鍵有反應」 |
| Runtime Debug 面板 | 「一堆跳動的數字」 |
| 141 Tests／0 B GC | 「兩個數字」 |

**五項的成功標誌全都是「隱形」。** 動畫與角色系統做對了，觀眾的感受是「正常」；做錯了才會被看見（滑步、同腳連踩、卡頓、掉幀）。

⇒ **展示的其實是「這裡沒有 bug」，而「沒有 bug」是預設期待，不是成就。**

這是架構型作品集的**結構性困難**，不是表達能力問題。水電做得好的房子，外行走進去只會覺得「這房子很正常」。

**推論（本檔所有策略的來源）**：既然「做對的樣子」不可見，唯一可行的方向是**先讓觀眾看見「做錯的樣子」**。所有翻譯、剪輯、排版規則都是這一條的展開。

## 2. 第二個診斷：優化錯了讀者

台灣的 HR 關卡通常用三件事篩：**JD 關鍵字對齊 ＋ 學經歷 ＋ 作品「看起來完不完整」**。
HR 的職責不是評估技術深度——沒有被賦予這個職責，也沒有這個訓練。

⇒ **「讓 HR 看懂架構」是一個永遠不會被該讀者評估的維度。** 把力氣花在那裡，投入報酬率是零。

過 HR 關的實際槓桿只有兩個：

1. **履歷關鍵字對齊**（Unity／C#／動畫系統／工具開發／效能優化／可測試架構）。
2. **作品看起來像完成品**。

第 2 點是目前真正吃虧的地方：

| 東西 | 外行看到的形狀 |
| --- | --- |
| Character framework demo 場景 | 「一個人在空地上走路」 |
| 背包／任務系統 | 「一個遊戲的一部分」 |

**這是可以修的，而且不用動架構**——給 demo 場景一個看起來像遊戲的殼（一個小關卡、一個目標、一個 UI、一個計時）。成本約 2–3 天，直接解掉「看起來不完整」這個扣分項。

## 3. 翻譯表：術語 → 痛點

**規則**：每一句都必須**先出現「壞掉的樣子」，再出現做法**。觀眾要先看見問題，才會覺得解法有價值。
開場一律先花 **10–15 秒**講清楚「這段要展示什麼問題被解決了」，再進技術。

| ❌ 不要說 | ✅ 改成說 |
| --- | --- |
| Walk／Run／Sprint 平滑切換 | 「鍵盤只有『按下／沒按』兩種狀態，但角色需要走→跑→衝刺三段速度。直接切會瞬間跳。我讓速度平順爬升，而且**動畫混合和實際位移吃同一個值**，所以全程腳不會打滑。」 |
| Stop 依腳相選片（`_LU/_RU`） | 「角色停步時如果選錯腳，會出現同一隻腳連踩兩次——這是最刺眼的動畫錯誤之一。我讓系統讀當下的腳步相位，自動決定用左腳還是右腳的版本收步。」 |
| 即時中斷／打斷優先級 | 「打擊感有一半來自『能不能取消』。我把誰能打斷誰做成一張**資料表**而不是寫死的 if——改一個數字，就能從『翻滾可以取消攻擊』變成『不能』，不用動程式。」 |
| 資料驅動 / ScriptableObject | 「調手感的人不該需要會寫程式。速度、跳躍高度、打斷規則全部住在資產裡，企劃自己在 Inspector 調，改完立刻看得到。」 |
| 單一寫入者 / 黑板 | 「大部分角色控制器爛掉的原因是『這個數值到底誰改的』沒人說得清。我讓每個數值只有一個地方能寫，而且**寫錯的話測試會紅**。」 |
| 141 EditMode Tests | 「架構壞掉通常**沒有任何症狀**，要等半年後加新功能才發現。所以我把架構規則本身寫成測試——有人違規，測試會紅，而且直接告訴他違反了哪一條。」 |
| 0 B/frame GC | 「手機遊戲掉幀最常見的原因是記憶體回收。我讓角色系統每一幀不產生任何垃圾，有 Profiler 實測截圖。」 |
| Foot IK | 「角色走在斜坡上，腳會插進地面或浮在半空。我讓兩隻腳自動貼合地形，但**姿勢優先於貼地**——寧可腳沒完全貼齊，也不要為了貼地把腿拉成不自然的角度。」 |
| ADR／架構決策紀錄 | 「每個重要決定我都寫下**為什麼這樣做、以及否決了哪些替代方案**。這樣半年後接手的人不會把我已經試過失敗的路再走一次。」 |

## 4. 三層讀者：內容分配

**不是簡化，是分層。** 同一份作品，三個入口，深度遞增。

| 層 | 讀者 | 停留時間 | 要放什麼 | 絕對不要放 |
| --- | --- | --- | --- | --- |
| **L0** | HR／人資 | 3 秒 | 一句話定位 ＋ 一張會動的圖 ＋ JD 關鍵字 | 架構圖、ADR、測試數字 |
| **L1** | 用人主管 | 30 秒–2 分 | 解決了什麼問題、你的角色、可驗證的成果（0 GC 實測、工具省下多少人工） | 型別名稱、管線順序、介面簽名 |
| **L2** | 技術面試官 | 3 分鐘＋ | 架構文件、ADR、**被否決的方案**、取捨與代價、已知限制 | — 這層要多深有多深 |

**關鍵**：L2 的東西**放在連結後面**，不要放進影片。技術面試官會點進去，HR 不會——這樣剛好各取所需，而不是互相稀釋。

## 5. 展示手法：把「證據」放進畫面裡

**GPT 式 A/B 展示（換資料→行為改變）的弱點**：觀眾無法驗證你真的沒改 code。畫面打一行「No controller code changes」是**宣稱**，不是證據。

⇒ 升級方向不是換題材，是**讓證據出現在畫面內**。

### 5.1 成本 ≈ 0（已存在的能力，只是沒拍）

| # | 手法 | 為什麼有效 |
| --- | --- | --- |
| **A** | **紅燈示範**：故意違規（技能層呼叫 `MotionDriver`／加第二個黑板寫入者／加一個 `StateType`），跑 EditMode → 架構測試依序變紅，**錯誤訊息本身寫著違反哪條原則、擁有者應該是誰** | 整份作品集裡**唯一**能證明「架構不是文件宣稱、而是可執行約束」的東西。幾乎沒人這樣做。外行看到紅色失敗訊息也懂「他寫了規則，而規則會擋人」 |
| **B** | **換 `GaitProfileSO` 資產換掉整套操作手感**（Souls-like hold-sprint ↔ ARPG toggle-walk），0 行程式 | README 已宣稱這個能力，但零畫面在證明它。最便宜的「換資料換行為」 |
| **C** | **踩過的坑做成 15 秒 before/after**：`Move(Vector3.zero)` 把 `isGrounded` 打成 false 連鎖出假的 `JustLanded`／用 Mixer root 加權時間查腳相導致同腳連踩／暫停中放開 Alt 把游標鎖回去 | 三個都有明確的錯誤畫面、明確的根因、明確的最小修正。**技術面試官對「你怎麼找到這個 bug」的興趣遠大於「你做了幾個功能」**。素材 100% 已在磁碟上 |
| **D** | **`git diff --stat` 放在畫面旁邊**：新增動作時 Core／Pipeline = 0 lines changed | 把宣稱變成可驗證的數字。與 A 搭配最強：**A 證明「不能亂改」，D 證明「不需要改」** |

### 5.2 要寫一點新東西（挑一個就好）

| # | 手法 | 成本與風險 |
| --- | --- | --- |
| **E** | **換 producer 而不是換動畫**：把 `PlayerLocomotionPolicy` 換成 `ReplaySource`（錄一段 `MovementIntent` 再播回去）。畫面上**沒有人碰鍵盤，角色照跑，Runner 零改動** | 一顆小 class。ADR-003 §11 早已列為「加法擴充」⇒ 這是**把宣稱變成證據**，不是為作品集造新系統 |
| **F** | **Ownership HUD**：畫面上標出本帧順序 1→7 各跑了什麼、**現在誰擁有位移權**、哪些仲裁旗標亮著 | 對「外行看不懂」的直球解法——不用他推理，字寫在畫面上。但屬 Editor 工具，要過 CLAUDE.md 的 Gate A／B |

### 5.3 挑選原則（不可違反）

> **只拍已經存在的能力，或本來就排在路線圖上的東西。**

不要為了作品集去建新系統——那會變成專案文件裡反覆否決的「為想像中的需求預造」，而**那份紀律本身就是作品集的一部分**。用一個平庸的新系統換掉一個有深度的舊系統，是虧的。

## 6. 反向框架：「如果你在做 X，我能解你什麼問題」

來自美術朋友的回饋，是整輪討論裡最有價值的一句：

> 假設我們真的合作，我現在在做一款 2D 的遊戲，你會覺得有哪些技術難點是你可以幫忙解決的？

它把敘事從**「我做了什麼」**翻轉成**「我能解你什麼問題」**——後者才是用人主管腦裡真正在問的。

### 6.1 標準答案（2D 版，示範用）

> 1. **輸入手感**：2D 平台遊戲的手感有一半在 coyote time／jump buffer／input buffer。這些最常見的死法是全部散在 `PlayerController` 裡互相打架，改一個壞三個。我做的就是把「輸入 → 意圖 → 狀態」切開，每個值只有一個人能寫，所以加一個 buffer 不會弄壞既有的。
> 2. **動畫與邏輯解耦**：2D 一樣會遇到「攻擊動畫沒播完不能移動」然後狀態機爛掉。我的做法是動畫層只是一個 sink，gameplay 不去查動畫在播什麼。
> 3. **手機效能**：我做過每幀零 GC 的角色系統，有 Profiler 實測。2D 手遊掉幀最常見的原因就是這個。
> 4. **工具**：2D 更吃關卡／敵人／對話的配置。我做過批次烘焙工具鏈，把美術要手動跑的流程變成按一顆按鈕。

**注意四點裡沒有一句提到 3D、Foot IK、Locomotion。**
⇒ 能力本來就不綁維度，**綁死在 3D 角色上的是敘事，不是能力**。

### 6.2 可轉移能力清單（換任何專案類型都適用）

| 能力 | 一句話證據 | 適用於 |
| --- | --- | --- |
| 分層與單一寫入者 | 每個黑板欄位有 Owner／Writer／Readers，且由測試守 | 任何有狀態的系統：背包、任務、戰鬥、UI |
| 資料驅動配置 | 手感／規則住 ScriptableObject，企劃自調 | 任何需要非程式人員調參的專案 |
| 可執行的架構約束 | 架構規則寫成 EditMode 測試，違規變紅 | 多人協作、長期維護的專案 |
| 零 GC 熱路徑 | Development Build Profiler 實測 0 B/frame | 手機、主機、任何吃幀率的專案 |
| 編輯器工具鏈 | 批次烘焙／特徵提取／驗證 Gate | 任何有重複人工流程的團隊 |
| 中斷與優先級仲裁 | 誰能打斷誰是資料表，不是 if | 戰鬥、技能、對話、過場 |
| 決策文件化 | ADR 含**被否決的方案**與否決理由 | 任何需要交接的專案 |

## 7. 具體重組提案

| 位置 | 內容 | 理由 |
| --- | --- | --- |
| **主打 1** | **工具＋資料驅動**。入口**不要從 locomotion 進**，從「換一份資產，角色行為就變了」進。畫面：Inspector 改值 → Play → 行為改變 → 旁邊 `git diff --stat` 顯示 0 lines changed | **工具向是唯一一種「架構能力」可以被外行直接看見的形態**——工具的價值就是「本來要做十次的事現在做一次」，這個概念不需要懂程式 |
| **主打 2** | 戰棋工具（同樣工具向，外行友善） | 朋友也點名了這個 |
| 其餘 | 各三行列點帶過 | 作品集塞太多會讓人抓不到重點 |
| **L2 深度** | 架構文件／ADR／被否決方案，**放連結後面** | 面試官會點，HR 不會，剛好各取所需 |
| **殼** | 給 demo 場景一個像遊戲的目標（小關卡＋UI＋計時） | 解掉 §2 的「看起來不完整」扣分項 |

**單支影片的三段證據結構**：

```text
Adding Character Actions Without Rewriting the Controller

① 換資料新增動作   → Inspector 換資產，Play 生效
② 架構會擋下違規   → 故意違規，EditMode 測試變紅   ← 別人做不出來的就是這段
③ 核心零改動       → git diff --stat：Core/Pipeline 0 lines changed
```

①③ 到處都有人拍，**②沒有**。

## 8. 技能系統作為展示題材的評估

技能系統之所以被選為下一個切片，理由是**配現有框架且有含金量**（`docs/08-skill-system.md` §1 的三個缺口）。素材曾被視為唯一障礙，**2026-08-29 的資產盤點已解除這個障礙**（見 memory `kubold-action-catalog`）。

但盤點同時揭露一件事：**「工程上最小的切片」與「展示上最強的切片」不是同一個。**

**🔧 判準修正（2026-08-29，使用者指正）**：初版把「外行秒懂」當成單一維度，是錯的。它必須拆成兩層，而且**第二層才是展示價值的來源**：

| | ① 看得懂「這是什麼動作」 | ② 看得懂「這很難做」 |
| --- | --- | --- |
| 撿東西／拉拉桿 | ✅ | ❌ 他只看到一個人彎腰 |
| 丟出去的東西飛出去打到敵人 | ✅ | ✅ |
| 一隻會追你、被打會有反應的敵人 | ✅ | ✅ 「這是一個遊戲了」 |

`_LH/_RH` ＋ `_90` 的 selection 復用**只有工程師看得到** ⇒ 互動類是 **L2 素材**，不是展示素材。

| 候選 | 工程價值 | 展示價值（判準②） | 裁決 |
| --- | --- | --- | --- |
| `Fists_Punch_R`（站定瞬發） | ★★★ 最小、零位移、三條紅線全不碰 | ★☆☆ **容易被誤讀成「普通攻擊」** | `docs/08` 選它是正確的**工程判斷**；但**不當展示題材** |
| `PickUp_*`／`PullLever_*`（`_LH/_RH`＋`_90`） | ★★★ 真實 selection 維度，與 Stop 的 `_LU/_RU` 結構同構 ⇒ 免費證明「同一套 Selection seam 撐第二個 domain」 | ★☆☆ 過不了判準② | **延後**（L2 素材，給面試官看） |
| `Throw_Start`→`ThrowLoop`→**`ThrowCancel`**→`ThrowEnd*` ＋投射物 | ★★★ 含 **authored 取消動畫**，逼出「不可取消窗」裁決（`docs/08` §9.1 的 G1 判準②） | ★★★ **丟出去的東西飛出去＝無可爭議是技能**；零 VFX 依賴 | ✅ **採用為展示題材** |
| 敵人（`AIMovementSource`＋NavMesh 查詢） | ★★★ 兌現 ADR-003 §11 的 AI producer 宣稱；壓測 §9-L2 | ★★★ 有東西會動、會反應 ⇒ 立刻像遊戲 | ✅ **採用，且排在技能之前**（它是舞台） |
| `Vault1m`／`Slide`／`Climb2m` | ★★★ 位移權移交＋第一個真實 world target | ★★★ 翻越／滑鏟立刻可辨識為不同能力 | 延後（會同時觸發 G1②③，代價大） |

⚠️ **不要為了展示而調整工程順序**——那是本檔 §5.3 挑選原則的反面。
**允許的是「在已排進路線圖的項目之間重新排序」，不是「為了畫面新造系統」。**
本輪把敵人與 Throw 提前，依據是它們各自都已寫在 ADR-003 §11 與 `docs/08` §13.2 裡；
執行順序與任務分配見 `WORKLOG.md`「作品集最低限度衝刺」。

## 9. 一頁式檢核（寫任何文案前跑一遍）

- [ ] 開場 10–15 秒有沒有先講「什麼問題被解決了」？
- [ ] 有沒有先讓觀眾看到**壞掉的樣子**？
- [ ] 每個術語有沒有查過 §3 翻譯表？
- [ ] 這段是給 L0／L1／L2 哪一層看的？有沒有混層？
- [ ] 宣稱（「零改動」「可擴充」）有沒有**畫面內的證據**（測試紅燈／diff／Profiler 截圖）？
- [ ] 有沒有為了作品集去建路線圖上沒有的東西？（有的話停手，見 §5.3）
- [ ] 作品**看起來**完整嗎？（§2 的殼）
