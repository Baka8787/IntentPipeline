## 2. 逐題回答

### A. 成熟系統只改 IK 權重，還是構建依相位變化的目標軌跡／參考空間？

**構建目標，不是只調權重。** 三個系統都在「目標」這一側下功夫：
- **RJ** 擺盪軌跡是逐帧**構建**的：在上一個落腳點與預測的下一個落腳點之間插值，依地形切線加一段抬升弧避開台階，
  再抬到支撐腳所在的地面高度，最後把動畫原本的抬腳與側移**疊加**上去（§7.3.2–§7.3.7）。
- **AC** 每隻腳獨立預測落點（位置＋混合時間／比例），並把動畫的腳高重新解讀為「相對腳路徑」的高度（投影片〈Predictive Foot Motion〉）。
- **UE-FP** 以 plant／unplant 狀態、地面 trace、彈簧插值決定每隻腳的目標，節點的 alpha 只是整體強度。
- **U-IK**：Unity 的權重語意就是「0＝動畫原始位置，1＝目標」——只在 FK 與單一目標之間線性混合。
  ⇒ 在 Unity Humanoid IK 裡要表達「軌跡構建」，就是**逐帧構建目標、權重維持高值**；這正是 T1「權重＝1、目標由參考面構建」的形式。

**本地證據一致**：只調權重（M0／M1）在樓梯上兩難——權重高就滑行中貼地，權重低就穿進台階（`docs/05` §3.5.4.4）。

### B. 「擺盪時保留相對移動／參考面的軌跡，落腳時混向真實接觸面」是已知、站得住的模式嗎？

**是，而且幾乎是逐字對應。**
- **UE-FP** `simple_collision_influence`：擺盪中對齊簡化碰撞還是複雜碰撞的比例；說明直接寫到樓梯常用簡化的斜坡碰撞，
  追蹤簡化幾何可讓擺盪中的腳軌跡更平滑。——這就是「擺盪看移動面、落腳看真實面」。
- **AC**「動畫中的高度＝腳路徑上方的高度」「絕不讓腳低於腳路徑」；樓梯與峰頂用 **Ground Envelope**（沿腳路徑的地面點取**凸包**，得到連續路徑，「只給腳用」）。
  我們由產生器沿**踏面前緣連線**生成的移動面（`docs/44` §3），幾何上就是樓梯剖面的凸包。
- **RJ** 軌跡以前後落腳點之間的連續線為基準，再加動畫原本的抬腳（§7.3.7）；腳在落點附近才被落點約束完全接管（§7.2.2）。

### C. 過渡通常怎麼控制？

**組合，而且是連續的**：
- **UE-FP**：腳速來自動畫的速度曲線（`speed_curve_name`）；低於 `speed_threshold` 視為踩住，
  `speed_threshold` 到 `unalignment_speed_threshold` 之間是連續過渡，文件說這段應大致對應腳掌滾動期；另加 `distance_to_ground`（離落腳平面多近才完全對齊）。
- **AC**：接觸由**資料**定義（動畫標記的 Left／Right Contact 區段，自動產生）；產生依據是腳尖速度＋腳尖高度，再加「IK 姿勢過濾」
  （假設地面、解一次腳、檢查位置與旋轉誤差）得到信心值。預測另外提供混合時間／比例。
- **RJ**：由動作分析得到的關鍵時間點（抬腳、離地、觸地、踩實）與相位（支撐／擺盪／腳掌滾動），腳掌滾動期做插值。
- **MM**：動畫中腳尖幾乎不動時鎖住腳尖；接觸事件在動作資料上標記。

**與 T1 的對照**：T1 的 β＝高度 × 水平速度相位，用的是同一類訊號（高度＋速度）、也是連續範圍，方向正確；
差別在外部系統把速度／接觸放在**動畫資料**（烘焙曲線或標記），不是每帧有限差分。

### D. 接觸面本身是階梯狀時，怎麼避免目標跳變？

- **擺盪段**：不對離散面取樣——**AC** 用凸包 Ground Envelope（連續路徑），**UE-FP** 用簡化碰撞，**RJ** 用落腳點之間的平滑地面高度軌跡（S 形曲線）。
- **落腳段**：目標是**這一步的落點**，不是「腳現在正下方」：**AC**／**RJ** 都預測每一步的落點；**RJ** 指出預測會一直更新到觸地，
  且越接近落點、平滑越強（§7.2.2）。**UE-FP** 用彈簧插值（`floor_linear_stiffness` 等）追地面。
- **踩住之後**：鎖住（見 E／F），不再重新取樣。
- **對照 T1 的量測**：T1 目標每帧跳變 p99 9–15 cm，來源正是「落腳端取的是腳**當下**正下方的踏面（`GroundY`，還含抬升）」——
  β 上升期間腳還在跨階緣，踏面每帧換階。**這是外部系統明確避開的做法。**

### E. 責任劃分

| 責任 | 外部做法 | 我們 |
|---|---|---|
| 移動／碰撞面 | 膠囊走簡化碰撞；UE-FP 把它當成擺盪參考之一 | ✅ 產生式移動面（`CharacterMovementSurface`），只給移動與身體參考 |
| 擺盪軌跡 | 在連續參考（腳路徑／包絡／簡化碰撞）之上疊動畫抬腳；絕不低於參考 | ⏳ T1（移動面＋動畫離地高度） |
| 落腳／接觸 IK | 每一步一個落點；觸地附近才完全接管；接觸後鎖住，偏離過大才放開 | ❌ 目前是「當下正下方」逐帧取樣、沒有鎖腳 |
| 骨盆／身體 | **UE-FP**：可選「所有腿／只看踩住的腳／上坡看前腳、下坡偏低腳但避免過度壓縮」，可設定先抬腳跟或先降髖（`heel_lift_ratio`），上限 `max_offset`；**AC**：沿「上一落點→預測落點」坡度、以支撐腿決定（上下坡不同）、臨界阻尼彈簧去彈跳；**RJ**：每條腿算「保持原彎曲度」與「完全伸直」兩個高度，平滑合成（刻意避免 min 造成二階不連續），寧可多彎不可過伸 | ◐ 參考面包絡（常數下沉）——與 AC「沿坡度」同向，但深度不看落腳可達性、會碰上限 |

### F. 與我們觀察到的失敗模式對應

| 我們觀察到的 | 外部對應 |
|---|---|
| **IK 提早貼地**（動畫腳還以 6 m/s 滑行就被貼地） | AC：反應式 IK 被形容為遲鈍、看起來很程序化，改成預測式；UE-FP：用速度區間定義腳掌滾動期，而不是高度門檻 |
| **擺盪腳穿進台階** | AC 明列「小障礙、樓梯與峰頂」的腳穿透，解法是 Virtual Ground／Ground Envelope（凸包）；UE-FP：擺盪用簡化碰撞；RJ：依地形切線抬升 |
| **目標在踏面間跳變** | 外部都用「每步一個落點＋接觸後鎖住」，擺盪用連續路徑，不在離散面上逐帧取樣 |
| **骨盆過度補償**（碰 0.35 上限、半蹲） | UE-FP `max_offset`（超過就搆不到）、`max_offset_horizontal`（防止腳鎖住時髖降太低）、`heel_lift_ratio`；RJ：過伸會僵、取 min 會二階不連續 |
| **鎖到錯的階** | UE-FP `unplant_radius`／`unplant_angle` 與 `replant_*_ratio`（偏離過大就放開、滯後重鎖）；AC「不要完全鎖死」（鎖定／允許微滑／解鎖三態） |

## 4. 結論

**結論 2：T 系列方向正確，但實作前需要特定修改。**

外部三個獨立來源（UE 引擎節點、Assassin's Creed 量產系統、Unity Locomotion System 論文）都採用同一個架構：
擺盪軌跡建在連續的參考上（簡化碰撞／凸包包絡），動畫腳高是參考之上的高度，權重只是強度，落腳時才交給真實接觸面。
T1 的核心（參考面切換、權重＝1、保留動畫離地高度）與此一致，而且我們的移動面在幾何上就是 AC 所說的凸包包絡。

但 T1 在**落腳端**與外部做法不同，而那正是實測剩下的問題（目標跳變 p99 9–15 cm）：

1. **落腳目標要是「這一步的落點」**，不是腳當下正下方逐帧重取的踏面；並改用真實踏面高度（`GroundY` 含腳跟／腳趾抬升，擺盪中可高 10 cm）。
2. **加上鎖腳**：踩住後鎖位置、旋轉自由；偏離過大才放開、滯後重鎖。它同時讓支撐期不再重取踏面。
3. **（建議，非阻擋）** β 的速度／接觸訊號改由烘焙資料提供，對齊 UE 的速度曲線與 AC 的接觸標記；執行期有限差分作退路。
4. **骨盆不在 T 系列範圍內**，但外部都由踩住的腳與可達性決定骨盆；T 系列落地後再重評（root 離面距離仍是 Motion 層獨立議題）。

下一步（待使用者裁決）：依上述 1、2 修改 T 系列，先離線模擬「每步落點＋鎖腳」對目標連續性、穿透、觸地→擊發的影響，再送 Codex 審查。

## 6. 後續：「每步落點＋鎖腳」離線模擬（2026-09-25，使用者同意 §4 的 1、2 後執行）

**新資料**：探針在執行期對動畫腳的腳跟（−0.10 m）、腳踝、腳尖（＋0.15 m）三點下方打 `StairTread`＋`Default` raycast，
取得真實踏面高度（不含 IK 抬升）。評估基準改為「腳掌範圍內最高的踏面」——平底腳底低於它就一定插進台階。
模擬器：權重＝1、目標＝lerp(移動面, 落腳高度, β)＋動畫離地高度；β＝高度 × 水平速度相位（同 T1）。

| 變體 | Walk 樓梯支撐誤差 p95（上／下） | Walk 上樓擺盪穿透 p95 | 目標跳變 p99（Walk 上／下） | Run 上樓穿透 p95 |
|---|---|---|---|---|
| T1r：每帧、踝關節正下方的踏面 | 18.9／17.4 cm | 11.8 cm | 16.1／12.8 cm | 8.8 cm |
| **T1f：每帧、腳掌範圍內最高的踏面** | **3.1／2.9 cm** | **7.0 cm** | 13.4／11.4 cm | **1.5 cm** |
| T2a：預知的每步落點（未來資料）＋鎖腳 | 16.6／19.8 cm | 10.0 cm | 21.7／18.4 cm | 3.4 cm |
| T2b：β ≥ 0.5 時閂鎖落點（腳掌）＋鎖腳 | 16.6／19.8 cm | 10.0 cm | 9.6／10.0 cm | 3.4 cm |
| T2b＋腳下踏面換階就重新閂鎖 | 3.1／2.9 cm | 7.0 cm | 13.4／11.4 cm（等同 T1f） | 2.6 cm |

**發現**：
1. **落腳高度必須是「腳掌範圍的支撐」，不是單點。** 平地動畫的步幅不是踏面深度的整數倍，腳經常跨在階緣上落地；
   單點取樣會在上下兩階間翻動。改成腳掌範圍最高點，支撐誤差 17–19 cm → 約 3 cm，是最大的單項改善。
   （Foot IK 既有的腳跟／腳尖雙點採樣、以及 `GroundY` 的抬升，其實就是在處理這件事——它不只是擺盪時腳前傾的副作用。）
2. **在 β 門檻閂住落點，會鎖到錯的階**（16–20 cm）——正是 §2.F 的外部失敗模式；加上換階重閂則退化成每帧追蹤。
3. **預知落點也沒有更好**：動畫的支撐腳每步本身滑移 4–9 cm，不先鎖住水平位置，事先決定的落點很快就不在腳下。
   ⇒ 外部的「每步落點」必須和**鎖腳**一起才成立；而鎖腳改變的是腳的水平位置，離線資料只有動畫腳位下方的踏面，
   **鎖腳的效果只能在執行期驗證**（上表鎖腳變體的支撐誤差被這個量測限制扭曲）。
4. **平地的觸地→擊發變成 −6 帧**：T 系列讓畫面上的腳照動畫軌跡走（懸空 3–4 cm 後慢慢放平），畫面觸地（踝關節估計 ≤ 1 cm）變晚。
   腳跟著地時腳掌上翹，踝關節估計會高估腳跟高度，所以這個數字偏保守；需要腳跟位置才能定論。

**修訂後的建議（待 Codex 審）**：T3 ＝ T1f（腳掌範圍支撐高度）＋ 鎖腳（β≥0.95、腳慢、腳低時鎖水平位置與鎖定位置下方的腳掌支撐高度；
偏離超過半徑或 β 下降時放開，平滑放回動畫腳位）。不做「β 門檻閂落點」。以執行期原型＋探針驗證鎖腳，而不是再做離線模擬。

## 7. Codex 審查 T3（2026-09-25）

**結論**：可以做成執行期原型，沒有架構阻擋；但有 2 個 High 必須先改。

- **High 1——「腳掌範圍」的原則對，算法不對**：不是取三點下方地面的最高值，而是保留動畫的腳底朝向，
  算出「讓腳跟／腳踝／腳尖都不穿透所需的最小抬升」（Foot IK 既有 L1 最大穿透約束，搬到 T 系列的參考空間）：
  `swingAnkleY ＝ 移動面Y ＋ 動畫踝高`、`requiredLift ＝ max_i(0, 地面Y_i − (swingAnkleY ＋ 旋轉後腳底偏移_i.y))`、
  `目標Y ＝ swingAnkleY ＋ β · requiredLift`。取原始高度的最大值會在腳尖已經高過上一階時仍把整隻腳抬高，損害 Natural Pose。
  另須分清「踝高」（重建目標用）與「腳底離地」（＝踝高 − `FeetBottomHeight`，鎖腳條件用）。
- **High 2——位置權重與旋轉權重要分開**：`ResolveFoot` 目前兩者同值；「權重＝1」若照字面做，擺盪中腳掌也會被強制對齊地面。
  T3 應是「**位置**權重維持高值」，旋轉權重保留現行的支撐高度行為。
- **Medium**：①進鎖前跨階緣的跳變仍在（T1f 目標跳變 p99 11–13 cm）；β 只是把跳變縮小。若原型仍看得到，下一步應是「和水平鎖定一起決定的接觸候選」，
  不是再加權重淡化或平滑。②鎖腳需要明確狀態機：未鎖 → 鎖定 → 釋放中 → 未鎖；`ikAllowed` 為假、pose 無效、`OnDisable`、瞬移或巨大不連續時立即失效並重設速度歷史；
  不跨帧保存 `RaycastHit`／`Collider`，只存數值。③原型與探針必須用同一個遮罩（`GroundLayers`）再比數字。
  ④平地 −6 帧尚不能判定為退化：要先用帶朝向的腳跟／腳掌端點量測「腳跟著地、腳尖著地、全腳踩實」與擊發的時序基準。
  ⑤更正：目前 `ikAllowed` 只是 `IsGrounded && !BlockIK`，沒有任何來源會發出 `BlockIK`，所以地面上的 Hurt 並不會關閉 IK；
  T3 只能依這個條件反應，不能認狀態名稱。
- **沒有問題**：`FootIKController` 仍是 `FootIKTargetData` 唯一寫入者；每隻腳的鎖腳狀態屬於有意保存的演算法狀態（同骨盆平滑、`FootPlantTracker`），不違反「不跨帧保存帧內資料」；
  重用 `MovementCollisionMask`；零配置可達成；不需要 ADR（子系統內的演算法修訂）。`FootIKGroundData` 必須維持「本帧物理觀測」，腳步偵測器不受影響。
  修正 High 1 後 T3 不縮小擺盪活動範圍；鎖腳只在接觸期、有放開邊界，是接觸約束，不是被禁止的 Fade／Gate。

**原型前要做的**：①以 High 1 的最小抬升算法取代「最高踏面」；②分開位置／旋轉權重；③鎖腳狀態機與失效路徑；④探針改用 `GroundLayers`；
⑤先量帶朝向的腳跟／腳尖接觸時序基準。原型的驗收：目標跳變、擺盪穿透、支撐誤差、鎖定期間鎖定點與動畫腳位的偏離、釋放期的腿長可達性、觸地→擊發（以腳跟接觸為準）。

## 8. T3 執行期原型（2026-09-25，🧪 X Bot 開啟、Y Bot 關閉；**Trial 前的原型，尚未人工 Play 驗收**）

### 8.1 實作（`FootContactSolver.cs`＋`FootIKController.ResolveContactPosition`，開關 `FootIKSettings.UseContactPrototype`）

關閉時舊路徑逐位元不變（Codex 確認）。開啟時只改**位置**目標與位置權重；旋轉目標／旋轉權重、骨盆、`FootIKGroundData`（腳步偵測器的輸入）都不動。

1. **一帧外插**：目標在第 N 帧 LateUpdate 算、第 N+1 帧套用。位置權重為 1 時不外插，擺盪腳會落後動畫一帧（實測 Walk 7.5–10.5 cm、Run 11–16 cm）；外插後殘差 p50／p95 約 1／2–4 cm。
2. **β ＝ 支撐量 × (1 − smoothstep(1, 4 m/s, 動畫腳水平速度))**（同 T1）。
3. **擺盪參考**：目標水平位置下方的移動面（碰撞矩陣推導的遮罩）＋ 動畫踝高。
4. **帶朝向的有號最小抬升**（Codex High 1 的修正版）：以即將顯示的腳朝向（pose 旋轉朝 IK 旋轉目標依旋轉權重 slerp）取腳跟／腳踝底／腳尖，
   `delta ＝ max_i(地面_i − 端點_i.y)`；`lift ＝ delta ≥ 0 ? delta : β·delta`——穿透一律抬起，懸空只依 β 下拉。
   （§7 的 `β·requiredLift, requiredLift ≥ 0` 會在擺盪中留下 (1−β)·穿透，也無法把腳從移動面拉到較低的踏面；Codex 同意此修正。）
5. **鎖腳狀態機**：未鎖 →（β ≥ 0.95 且上一帧有即時接觸）→ 鎖定（只鎖水平；鎖在當帧外插後的動畫位置，不跳）→
   （β < 0.7／離動畫腳 > 0.2 m／上一帧失去即時接觸）→ 釋放中（0.12 s smoothstep，水平與高度共用同一權重，高度以接觸底線為下限；🔄 §9：水平改為「當下動畫腳位 ＋ 衰減中的凍結偏移」）→ 未鎖；
   釋放完成前不得重鎖。失效：IK 不允許／pose 無效／元件停用（`isActiveAndEnabled`——管線不看啟用狀態）／原型關閉 ⇒ 整體重設；瞬移（> 0.5 m／帧）⇒ 鎖腳重設、不外插。
6. **鎖定支撐**：鎖定當帧記下決定抬升的那一點（腳跟／腳踝底／腳尖）與其地面高度；鎖定期間**只有那一點**以 max(即時, 鎖定支撐) 為地面，其他點照即時查詢；
   接觸是否有效只看即時命中。

### 8.2 實作中的發現（都由執行期量測抓到）

### 9.1 釋放時機——**不是**骨盆需求的槓桿

- 診斷：樓梯上的釋放**全部**由 β 觸發（半徑從未觸發）。觸發時鎖定點在髖部後方 0.38–0.44 m，但**動畫自己的腳**也已在 0.32–0.37 m；
  釋放 0.12 s 期間目標被拖到 p90 0.50–0.62 m（動畫腳 0.39–0.55）。鎖腳本身只多拖 5–10 cm。
- 需求（不夾限，p05／p10）：各種釋放規則（凍結偏移釋放、0.06 s、UnlockBeta 0.85、「比動畫多拖 5 cm 就釋放」）都只動 0–1.1 cm（p10 最多 3.8 cm）；
  **完全拿掉鎖腳也只有 0.5–3.5 cm**。原因：被拖著的後腳，支撐量已經掉下來，不決定需求。需求的最壞情況 −33～−53 cm 來自動畫本身的落腳位置對上踏面高度。
- 但釋放時機影響**看得到的**問題：釋放中的後腿被拉直、腳搆不到目標 ⇒ 做 F1（§9.3）。

### 9.3 F1：凍結偏移的釋放（已實作，屬 T3 原型）

釋放期間目標 ＝ **當下**動畫腳位 ＋ smoothstep(ReleaseBlend) × 釋放開始那一帧凍結的（鎖定點 − 動畫腳位）。
舊寫法是朝留在原地的鎖定點插值——動畫腳一離開，目標就越拖越遠。轉移當帧的目標正好是鎖定點（偏移與傳進 `StepLock` 的動畫腳位同一個參數凍結）；結束時殘差 < 0.5 mm。

| prototype Run | 0.07／0.15 → 0.03／0.08 | 53% → 53% | 25.4 → 19.5 |

其他指標幾乎不變（鎖腳次數、腳步、漂移、垂直加速度相同）；代價：`Stairs (1)` Walk 擺盪穿透 > 3 cm 3% → 5%、Run 水平加速度 p99 +3～14%（釋放中的腳立刻跟上快速的動畫腳）。
測試：EditMode 689／688／1 既有略過（改寫釋放測試：落後量只會縮小、不超過開始時的差距）；PlayMode 97／96（既有 C0）。

### 9.4 Run 剩下的釋放問題＝擺盪參考（F1b，⛔ Codex 判定尚未可實作）

T3 擺盪目標 ＝ 腳下移動面 ＋ 動畫踝高，但 root 在樓梯上比移動面高（Walk 6–11 cm、Run 上樓 16–22 cm）⇒ 後腳目標比身體預期的低。
粗估「擺盪高度加 (1−β)·root 離面距離」可把 Run 釋放＋擺盪搆不到的 p95 從 15／27 cm 降到 4／14 cm。Codex 指出三個問題，**暫不實作**：
①真正經過最小抬升後的效果是 (1−β)²，粗估高估；②root 支撐射線在 LateUpdate 之後、`PosePlaneY` 在之前（樓梯上差 5–8 cm），且「在不在代理面上」是布林切換（Run 差 16–22 cm）——不連續；
③它改變 §3 的擺盪語意（移動面相對 → 部分 root 相對），若要做必須明確修訂規格。

### 9.5 Codex 審查

- 大方向成立：釋放時機不是需求槓桿；F2 是唯一實質降低幾何需求的候選，但在包絡骨盆下不會讓半蹲變淺。
- 修正：§9.1 的釋放規則表原本用夾限後的數字（−35 是被截掉的，不是物理需求）⇒ 已改用不夾限數字，結論縮窄為「F1 對 p05 幾乎無影響、其他規則可動次要百分位數公分級，都解決不了 30–53 cm 的最壞情況」。
- 建議只實作 F1，並如實歸類為「釋放品質修正」，不是「降低需求」；F1b、F2、「多拖 5 cm 就釋放」（需要髖位）都暫緩。

### 9.6 結論與下一步（待使用者）

- **在包絡骨盆不變的前提下，需求端的兩個槓桿都不會讓半蹲明顯變淺**：釋放時機幾乎不動需求；腳端可達性最多淺 5–8 cm，而且包絡不會用到它。
- 要真的站直，需要**同時**改骨盆（`docs/05` §3.5.4.5）與降低需求；而需求的每步變化 16–38 cm 主要來自平地步幅踩在樓梯上——這是樓梯用 clip 才能處理的部分（磁碟上沒有，需要新素材）。
- 可選的下一步：(i) F2 做成精確重播（接觸取樣＋旋轉權重）再評估，搭配日後的骨盆折衷；(ii) F1b 先定義同時基、連續的 root 離面來源；(iii) 找樓梯用 locomotion clip。

## 10. Landing-surface continuity：擺盪腳的落腳面太晚切到最終踏面（2026-10-03；⛔ 只量測，runtime 未改）

### 10.1 問題（使用者 Play，2026-10-03）
斜著上／下樓停步時，尾腳（或煞車腳）落在與支撐腳**不同階**：收步前半段看起來仍以「支撐腳那一階」為目標，快結束時才突然往上／往下移到真正的最終階。上樓、下樓方向相反。
與 `docs/46` §35（骨盆）無關，獨立處理。

### 10.2 方法
- throwaway `LandingSurfaceProbe.Probe_DiagonalStopLanding`（PlayMode，Explicit）：兩道樓梯 × Walk／Run × 上／下 × 斜向 0°（對照）／20°（放開前最後 2.5 m 向右偏）× 13 個放開位置 ＝ **208 次停步**。
- 記錄元件 `[DefaultExecutionOrder(32000)] LateUpdate`（IK 解完之後）逐帧記兩腳：T3 相位、β、lift、目標、動畫踝、**移動斜坡高度**（以 T3 同一條射線重算）、**踏面高度**（`GroundLayers`，與 T3 接觸取樣同起點）、預測落點（`TryPredictStopLandingGoal`）與其下方踏面。
- 分析：`docs/artifacts/pelvis-analysis/landing.py.txt`。

**T3 對未鎖定腳的目標（現行，§3 的擺盪語意）**：`target.y ＝ referenceY ＋ 動畫踝高 ＋ lift`。
- `referenceY` 的射線用**移動面遮罩**——在樓梯上打到的是 CharacterController 的移動斜坡（`CharacterMovementSurface`，沿踏面前緣連線），**不是踏面**。斜坡除了前緣之外都高於踏面（最多一個級高）。
- `lift ＝ ComputeMinimumLift(contactDelta, β)`：把目標拉向腳跟／腳踝底／腳尖三點**目前**所在踏面，權重隨 β（接觸程度）上升。
- ⇒ T3 隱含的落腳面 ＝ **斜坡 ＋ lift**（下稱 implied）。它只看「腳現在在哪」，沒有「這一步要落到哪」的資訊。

### 10.4 回答
1. **預測是否在 T3 切階之前就穩定指向最終踏面？** 是，多數情況：Walk 早 7–9 帧、Run 早 16–23 帧。但第一次可用時有 11%（17／153）錯一整階，全部是階緣站姿；而且 Run 煞車步完全沒有預測。
2. **T3 在什麼時候切？** 在**腳踝點跨過階緣**時（中位鎖定前 4–8 帧），之後隨 β 上升被 lift 拉到位；不是 ground miss（0 次）；T3 相位轉換很少是觸發點。骨盆求解器的 role 不進 T3 目標。
3. **上樓與下樓是否同一機制的正負版本？** 是。implied 落腳面追著「腳目前所在的那一階（＋斜坡）」走：下樓時它比最終階**高**，最後往下切；上樓時比最終階**低**，最後往上切。
4. **與 FU-14 是否同一底層問題？** 同一個家族（都是「只看腳目前 XZ 下方的地面」），但不是同一個缺陷：FU-14 是骨盆求解器的 Landing 角色**閃爍**（`SoleHeight` 以 FootIK 地面樣本計算、跨階緣時跳動）；本問題是 T3 擺盪目標的**延遲**——取樣本身穩定（A→B→A 1.7%），只是取的是現在而不是目的地。修好其中一個不會修好另一個。

### 10.5 「擺盪開始時 latch 預測落腳面」是不是最小修法？（評估，⛔ 未實作）
- **單獨 latch 不夠**：①11% 第一次可用就錯一階——latch 會讓腳整段瞄錯階，最後仍要切，而且可能更突兀；②Walk 的預測常在擺盪中段才出現；③Run 煞車步沒有預測。
- 量測支持的方向（待裁決）：
  - (a) **目的地取代「現在」**：擺盪中目標的落腳面從「腳下斜坡＋目前踏面」改成「這一步的目的地踏面」，並隨擺盪進度從起點階平滑過渡。目的地來源：有預測時用預測（並在跨階緣時以即時取樣驗證、偏差一階就以即時為準），沒有預測時（Run 煞車步）以動畫踝的水平速度外插落點。這會修改 §3 的擺盪語意 ⇒ 屬於 T3 contract 變更。
  - (b) **只處理 β 分量**：擺盪參考改用踏面而不是移動斜坡（§9.4 F1b 的同一題），讓同一階的 β 拉動消失；不處理跨階延遲。
- **不需要 toe／heel footprint 或遲滯**：腳踝點在階緣上是穩定的（A→B→A 1.7%、0 次漏打）；跳動來自「取樣的時間點」，不是取樣不穩。

### 12.3 回答
1. **Walk 最後落地提前幾帧穩定？** 鎖定前 9–12 帧，比 T3 早 7–8 帧。N 與結束站姿預測一樣，約在鎖定前 13 帧才出現（快照要等停步 clip 播放頭前進才生效）——**Walk 的提前量受這個時間點限制，不是受來源限制**。
2. **Run 煞車步能否在 20–24 cm 跳動前得到可信目的地？仍然不能**（0／35）。兩個可量化的原因：
   - **出現太晚**：N 在鎖定前中位 **8 帧**才出現（跳動在約 7 帧前）；煞車步的擺盪在放開按鍵之前就開始，而快照要等播放頭前進才生效。
   - **系統性偏差**：煞車步的 N 與實際鎖定點有幾乎固定的 **~9 cm 水平偏差**（第一次與最後一次出現時都是中位 8.8–9.4 cm）⇒ 只有 54% 落在正確的階。最後落地則準（1.2 cm）。推測與 §17 同類：Bake 的 plant 時刻（第一個「低且慢」的 sample）與 T3 鎖定時刻不同步。
3. **Run 最後落地是否不再需要位置／oracle 門檻？** 是。`HasNextPlant` ∧ 這隻腳 就足以判斷，不需要猜「是不是最後落地」：鎖定前 22–23 帧穩定、比 T3 早 9–14 帧（理想門檻是 27 帧）。差距來自 `RunFwdStop_RU` 同一隻腳兩次 plant（0.567／0.767 s）——第一個事件在第二次落地之前先被拿來當目的地。
4. **首次承諾錯誤率**：Run 最後落地 4／75（5%），Walk 最後落地 14／78（18%，§11 的 P 是 14%）。**整體沒有低於 §11 的約 11%**：Run 變好、Walk 略差。
5. **改答案次數與最晚修正**：Run 4 次、Walk 9 次；最晚都在鎖定前 1 帧（即時驗證）。「鎖定時錯」1–7 次全部來自即時驗證：我的三點取樣（只取 yaw）與 T3 鎖定時的支撐選擇規則不完全相同——Phase 2 接進 T3 時鎖定時的支撐本來就由 T3 決定（Locked authority 不變），所以這項不會成為鎖定後的錯誤，但代表鎖定前最後一兩帧仍可能有小幅修正。
6. **上／下樓**：同一份契約、同一套規則；兩個方向都有效。

### 12.4 Phase 1b 的結論（對照使用者的 Phase 2 前提）

- **Run 煞車步：不成立**——出現時間與偏差兩個問題都在。
- **Walk 中途落地：沒有目的地資訊**——resolver 必須輸出「沒有 intent」，T3 照現況處理。

## 15. Phase 1e：T3 support-surface semantics 的重現，與落地姿勢能否降低語意不一致（2026-10-03；⛔ 只量測，contract 與 runtime 皆未改）

**不是同一根因，但同一層**：兩者的位移都來自**動畫 pose**（A-1 是 LU clip 內容；B 是 crossfade／起始 phase），T3 只是在 β 掉下時釋放並跟隨；T3 自己的貢獻是 A-2 的一帧外插過衝（1–2 帧）與 B1 的 1–4 帧延遲。

### 20.1 A1 —— `RunFwdStop_LU` 的第二次左腳落地：地形感知選片需要什麼資訊（只分析，未實作）

**事實**
- Run 的變體**不在 Presentation 選**：`LocomotionModel`（Core/Movement）在放開當帧以 loop 的 `FootPhase`（`SelectByEntryPhase`，Run 立即選、不等 phase）決定 LU／RU。
- 選定的變體**同時驅動 root**：停步期間 `MotionDriver.ExecuteLocomotionStopMovement(variant.BakeData, …)` 用該變體的烘焙位移。⇒ 只在 Presentation 換 clip 會讓 root 與 pose 脫鉤。**決策擁有者必須仍是 `LocomotionModel`**；「Presentation 層」能做的只有提供事實。
- LU 的 re-step 在世界中一律 46 cm（§19.2）＞ 踏面深 27–34 cm ⇒ **在樓梯上它必定跨階緣**；平地沒有階可跨。所以判準不需要逐落點精度，只需要「停步路徑上的地面是不是階梯」。

**選片需要的資訊（與來源）**
| 資訊 | 來源 | 現況 |
|---|---|---|
| 各變體的 plant 排程（哪一次是同腳 re-step、在 root 空間哪裡、何時） | `MotionBakeData.FootPlantSchedule` | ✅ Core 已讀（ADR-010 D5） |
| 選片當下的 root 位置／朝向 ＋ 到 re-step 時的 root 位移 | `LocomotionModel` ＋ Bake 位移曲線 | ✅ 已有（預測快照的同一套） |
| **re-step 起點與終點下方的踏面是否不同（或：停步路徑上是否為階梯地形）** | 需要一個**地形查詢**：踏面層（不是 CharacterController 的移動斜坡——樓梯上那是平滑的 `__StairMovementSurface`，看不到階） | ❌ Core 沒有踏面層遮罩；只有 FootIK 的 `GroundLayers` |

**不建立 FootIK → 選片依賴的做法**：地形查詢放在 Core.Environment（已有 `TraversalProbe` 先例：Core 內自帶 LayerMask 與射線），由 `LocomotionModel` 在選片當下呼叫，或由一個環境感測器寫成黑板事實（後者動到黑板 schema ⇒ 需要 ADR）。⚠️ 兩者都需要 Core 自己的「踏面層」設定——與 FootIK `GroundLayers` 指向同一批層但分開持有（重複設定的維護成本要先接受）。

**各選項的代價（已量到的部分）**
| 選項 | 代價 |
|---|---|
| 樓梯上**立即**改選 RU（phase 不匹配） | 在錯的腳相進入停步 clip ＝ 與 B 同類的 crossfade 貼地滑動（§20.3 量到起始 phase 錯時可達 50–90 cm） |
| 樓梯上**等** RU 的入場 phase（Walk 的 pending 機制） | 最多半個 Run 循環 0.38 s × 4.7 m/s ≈ **1.8 m**（平均 ≈ 0.9 m）更長的滑行；RU 本身停步距離又比 LU 長 0.44 m（中位 2.14 vs 1.70 m）——Run 停步手感目前是刻意「立即選片」 |
| fallback：LU 第二次落地前淡入 Idle | 那時左腳在 root 後方 **59–61 cm**（§19.2 表）；Idle 雙腳在身體下 ⇒ crossfade 會把左腳貼地拖 ~60 cm，除非 IK 鎖住（＝回到「鎖到結束」）；另外 root 會少走 LU 剩餘的 ~19 cm 烘焙位移 |

### 20.3 B3 —— 起跑拖步：起始 phase 選擇 vs 縮短 crossfade（測試內介入）

**機制釐清**：Idle 與 Move 共用一個 locomotion mixer（key `Idle`）；「起跑」＝ 參數 MoveSpeed 上升、權重從 Idle 子狀態移到 Walk／Run 子狀態，而 Walk／Run 子狀態**從它當時的任意 normalized time 開始**（LU 停步後 0.33、RU 停步後 0.02）。RU 停步（1.5 s）比靜止 75 帧長 ⇒ 起跑時停步 clip 仍在淡出（兩個狀態）。
**為什麼改在平地**：樓梯上 root 會沿斜坡升降，動畫踝高度無法分辨「貼地滑動」與 root 垂直移動 ⇒ 樓梯版結果不可用（`Probe_RestartPhase` 保留但不採信）；平地版 `Probe_RestartPhaseFlat`／`Fine` 才是證據。
**指標**：每隻腳離地前（絕對高度離開起跑前 ±3 cm 之前）的水平位移——動畫踝（動畫本身）與最終骨骼（畫面）。

|---|---|---|

| φ 0.375 | 25.0 | 18.1 |
| φ 0.80 | 32.8 | 31.0 |
| **φ 0.88–0.92** | 動畫 L 2.7–7.6、R ≤ 1.6；畫面 **5.9** | 動畫 L 2.7–7.0、R ≤ 1.6；畫面 **6.7** |
| φ 0.96 | 6.1 | 54.9 |
| φ 0 ／ 1.0 | 77.4 | 71.1 |
