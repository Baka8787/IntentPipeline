生存與致死解剖

這個子系統的核心不是「HP 數字」，而是一個決定要在哪一幀被做出、被誰做出、以及被誰消費。 近戰與投射物的傷害在 Physics 階段結算，而 FSM、仲裁、HUD、重生四個下游都需要同一份真相—— 所以它必須排在整條管線的最前面。

01

責任邊界：五個環節，一個決定

誰決定「被打之後會發生什麼」

這個子系統橫跨 Core 與 App，但它只做一個決定： 這一下打下去，是「踉蹌一下」還是「倒地不起」。其餘四個環節都只是那個決定的下游。

⭐ IsDead 是 commit 的決定，不是讓讀者算 CurrentHealth <= 0
死亡是 CharacterHealth 做出的決定（含「已經死了就不再重複結算」這條規則），讀者只消費結果。
讓下游重新推導已 commit 的狀態，正是 docs/16-review-protocol.md 點名的本專案加重缺陷之一。
02

為什麼順序 0.5 必須存在

整條管線最早的一步

順序 0.5 不是「插在前面比較保險」。它有一個可以逐項驗證的時序論證， 而且三個下游各自依賴它的不同性質。

依賴 0.5 的下游依賴它的什麼性質放在 0.5 之後會怎樣
DeathState.CanEnter（順序 4）本幀的 IsDead 是最新真相死了還走一幀
AIMovementSource（順序 2.5）同上——它直接讀 IsDead 停止產生意圖屍體繼續走向玩家
AICombatContextSource（順序 2.4）🆕本幀的 JustTookDamage（受擊 ⇒ Provoked 交戰）；自己 IsDead ⇒ 不寫語境受擊後晚一幀才追；屍體仍發布交戰
HurtState.CanEnter（順序 4）JustTookDamage 這一幀有效受擊反應晚一幀或整個漏掉
DeathArbiterSource（順序 4.5）只需要 IsDead，不要求同幀（本來就是下一幀生效）
⚠️ 同幀論證只適用於 Physics 階段結算的傷害
MeleeHitboxSink 與 ThrownProjectile 在 Physics callback 結算，早於所有 Update ⇒ 本幀順序 0.5 發布的就是最新真相，上表成立。
但 GroundEffectSink.Release() 是由順序 4 的 ActionState 呼叫的， ApplyDamage 發生在 Update-time ⇒ 該角色本幀的順序 0.5 已經跑完。 加上不同角色的 Update 之間沒有明文執行順序，AoE 傷害不保證同幀發布， 最晚會在目標的下一次順序 0.5 才成為真相。
📌 這不是缺陷——只是「同幀停下來」這個保證的適用範圍比整句話窄。
⭐ 「死後停止產生 intent」為什麼不寫在輸入層
ADR-009 D1 的原始讀者清單含 AIInputSource／PlayerInputSource， 但同一份 ADR 的 §4.1 已正式修訂：改走 DeathArbiterSource → BlockInput。
理由不是偏好，是既有不變量推出來的—— A27_AttackTrigger_IsProducedByInputSourceOnly 的核心契約是「攻擊 trigger 只能由 IInputSource 產生」；它另外以 token scan 對現行的 AIInputSource 這個檔案 守住「不得出現 PlayerRuntimeData／FSM／ActionState」。
⚠️ 範圍要講準：那是針對該檔案的斷言， 既不是掃描所有 IInputSource 實作的通則，也不是「所有 producer 都不得讀 gameplay state」。
⇒ 準確的說法是兩句：①順序 1 的 IInputSource（現行兩個實作）不直接讀 Survivability；②在 IMovementIntentSource 實作中，只有 AIMovementSource 直接讀 IsDead。
直接讀 data.Survivability.IsDead 的七個型別身分讀它做什麼
AIMovementSourceproducer（MovementIntent）屍體不產生移動意圖
DeathArbiterSourceproducer（仲裁請求）BlockInput = IsDead
CharacterFacingSourceproducer（facing 請求）死亡否決層——不送 request
DeathStateconsumer（FSM）CanEnter ／ CanTransitionAway
MotionDriverconsumer依 profile 的 ApplyWhileDead 決定套不套用
HeadLookControllerconsumer（表現層）屍體不轉頭
WorldSpaceHealthBarconsumer（App）血條顯示
分佈

七個直接讀者裡有三個是 producer——這正是「死亡由各自的消費者明確收手， 不靠下游剛好擋住」這條紀律的實際樣子：每個 producer 自己知道該在死亡時停手， 而不是指望某一層擋住全部。
⚠️ 上表不含 CharacterHealth 自己（它是寫入者）。

另一條通道

PlayerCombatContextSource 不在上表——它讀的不是自己的黑板， 而是候選目標的 GetComponentInParent<CharacterHealth>().IsDead。
用途也不同：上表七個都是「我死了所以我收手」，它是「那個目標死了所以不合法」—— target validity，不是自我抑制。
⚠️ 附帶一條契約：沒有 CharacterHealth 的目標視為合法（訓練樁、可互動物件）。

03

兩個單幀邊沿：第四種復位語意

整體覆寫即復位

JustTookDamage 與 JustDied 是單幀事件， 但它們不走順序 7 的 ResetTransientState—— 這是 cross-system-contract 那三種語意之外的第四種組合：邊沿語意 ＋ 覆寫式復位。

欄位什麼時候抬起怎麼復位⛔ 不會發生的事
JustTookDamageApplyDamage 未致死時 _pendingHurt = truePublishTo 寫出後立即清除；下一幀整區覆寫自然回 false不排隊、不補播
JustDiedApplyDamage 致死那一行 _pendingDeath = true同上，逐字同構不讓下游各自快取上一幀 IsDead 去猜
⭐「不排隊、不補播」是語意，不是簡化
被 Roll／Traversal 擋掉的那一次受擊反應就是要被丟棄——翻滾的無敵幀結束後補播一次踉蹌是錯的。 傷害與扣血照常成立（那是 CharacterHealth 的事），只有表現被丟棄。
若改用單調計數器，CanEnter 會在 Roll 結束後才變真 ⇒ 正好做出錯的行為。
對稱性

JustTookDamage → HurtState 與 IsDead → DeathState 是完全對稱的： 同一個寫入者、同一區、同一個發布點。docs/26 §I 比較過四種 seam（Intent／注入／ PresentationEvents／Survivability）後選了這一條，正是因為它讓兩條路徑形狀一致。

互斥

致死時刻意不抬 JustTookDamage。抬了會讓 Hurt 與 Death 在同一幀爭同一顆 FSM——那正是 ADR-009 D2 要消除的決策擁有權問題。

重生

Revive() 一併清掉 _pendingHurt 與 _pendingDeath： 若在「pending 尚未發布」與「死亡」之間重生，殘留旗標會讓角色一復活就踉蹌一下或播一次死亡音。

04

Authority：三條分離線

誰決定什麼
角色可以寫⛔ 不可以
CharacterHealthSurvivabilityData 全區（唯一，A5 守）不知道重生點、傳送、collider——那些是 RespawnController 的事
攻擊方 sink呼叫 ApplyDamage(amount)不得直接送受擊請求（D2）——它不知道會不會致死
RespawnController協調：先傳送、歸零、還原，再呼 Revive()不寫 transform.position——MotionDriver.Teleport() 是唯一瞬移入口
DeathArbiterSource回報 BlockInput = IsDead不寫黑板（由 ArbiterPipeline OR 合併後整體覆寫）
PlayerHud／WorldSpaceHealthBar—只讀、只畫、零決策、零新增黑板欄位
authority ／ orchestration 分離
Revive() 只負責 survivability：血量與死亡旗標。 它不知道「重生」這個概念存在。
而 FSM 怎麼知道角色復活了？它不被通知，它只是照常讀黑板—— 下一次順序 0.5 的 PublishTo 把 IsDead = false 發布出去， DeathState 於同一幀的順序 4 看到後自然放行（CanTransitionAway => !IsDead）。 ⛔ Revive() 不呼叫 FSM、不送事件、不認識 StateType。

對稱

雙方 HP 與近戰傷害都是 100／25 ⇒ 四下互相致死。 這是刻意的對稱起手值（docs/26 §K 的第一版數值），不是平衡設計。

06

Failure case：三個同時存在的靜默缺陷

docs/26 §K

這個切片收尾時，一次修掉三個各自獨立、但都沒有任何錯誤訊息的缺陷。 它們的共同點是「一個功能從來沒有觸發過」——而那最容易被當成「還沒做」。

缺陷為什麼沒人發現失效模式
玩家從來沒有受擊反應敵人的拳頭從來不造成傷害（下一列），所以沒有輸入可以觸發它F5 authored
敵人拳頭從來不造成傷害命中鏈接線缺一環，而動畫照播、特效照出F5 authored
兩隻角色都沒掛 CharacterHealth程式完全正確地在一個不存在的元件上什麼都沒做——_characterHealth?.PublishTo() 是 null-safeF5 authored
🔴 可推廣：?. 讓「缺件」與「正常」長得一模一樣
順序 0.5 寫的是 _characterHealth?.PublishTo(_runtimeData)—— 這個 null-safe 是刻意的（`CharacterHealth` 是可缺席能力，見 cross-system-contract）。
但它的代價是：沒掛元件與掛了但沒受傷在執行期無法區分，兩者都是「什麼都沒發生」。 這正是 PrefabWiringTests（Verification Ladder L1）要在 EditMode 先擋一層的理由。
另一條

Hurt 的 bake 不可驅動 gameplay：受擊動畫的 root motion 是無號速度， 乘上 forward 會讓受擊把角色往前推 1.13 m——被打反而衝向攻擊者。 所以 HurtState.OnUpdateMotion 走 ExecuteVerticalOnlyMovement，與 Death 同一條路徑。
