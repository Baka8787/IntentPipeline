表現層音效解剖

這個子系統裡有兩種完全不同的觸發語意： 一種是每幀讀一份廣播快照（腳步、落地、受擊、死亡、離地）， 一種是別人在做 gameplay 決定的那一次呼叫裡順便發生（施法、揮擊、命中）。 兩者的共同點只有一個：它們都不自己播放。 這頁講的是那個「不自己播放」為什麼是架構決定，而不是省事。

01

兩種觸發語意，同一個 authority

誰決定時機 ≠ 誰持有輸出

左邊那條是快照消費：每幀讀一次黑板上的廣播快照，讀到 true 就播一次。 右邊那條是 Action 生命週期回呼：ActionState 在段落邊界主動呼叫， 而那正是投射物生成、命中窗開啟、AoE 結算的同一次呼叫。 兩條路最後都收束到同一顆 AudioController。

觸發端語意時機來源播放位置自己播嗎
AudioController（腳步）快照PresentationEvents.Left/Right該腳的世界位置—（它就是持有者）
AudioController（落地）快照PresentationEvents.Landed角色位置—
AudioController（受擊／死亡／離地）單幀邊沿Survivability ／ JustLeftGround角色位置—
ActionAudioSink生命週期回呼ActionState.NotifyBegin / NotifyReleaseemitPoint，未指派則自身 Transform⛔ 不
MeleeHitboxSink回呼內的去重通過點TryRequestHit（與 ApplyDamage 同一刻）被打者 root⛔ 不
ThrownProjectile物理掃掠命中FixedUpdate 掃掠（與 impact VFX 同一刻）hit.point⛔ 不（用射手的 controller）
GroundEffectSink回呼Release（探地後）冰刺落點⛔ 不
為什麼

PresentationPipeline 的類別註解早就標記了這個問題： 「未來若多個 Controller 競爭同一輸出（例如兩個模組都要控制 AudioSource）， 屆時升級為表現層的輸出仲裁」。戰鬥音效正是那個「未來」。 若 ActionAudioSink／MeleeHitboxSink／ThrownProjectile 各自 AddComponent<AudioSource>()，一個角色身上會有五、六個彼此不知道對方存在的音源： 3D 設定要改六個地方、同時播放時誰也不讓誰、pitch 各自為政。 ⇒ 本角色的 AudioSource 由一個元件持有，其他人只說「播什麼、在哪裡播」。

抽了什麼

使用者的要求是「不要讓 Combat 直接依賴 Footstep 專用型別；要共用就抽最小通用層」。 ⭐ 結果是四項裡有三項根本不用抽：AudioDefinitionSO、AudioLibrarySO 本來就在 Presentation/Audio 且沒有腳步知識；AudioController 只加了一個 PlayAt。 真正動的只有一個名字——FootstepAudioSourcePool → AudioSourcePool， 因為它原本就一行腳步知識都沒有（Play 的參數只有 clip／位置／音量／音高）， 舊名字描述的是它的第一個呼叫者，不是它的職責。行為逐位元不變 ⇒ 零測試改動。

沒有測試守

docs/37 §4.2 寫「Combat 端沒有任何一行 using 指到 Footstep 型別 ⇒ 由 ArchitectureRegressionTests 的 LayerRules 白名單維持」。 前半句我逐檔驗過，成立；後半句不成立。 A4 的 Presentation 那條規則整層遞迴且白名單列的是 Project.Presentation（前綴比對）⇒ Presentation/Actions/*.cs 若寫 using Project.Presentation.Footstep; 會直接通過。 📌 記在這裡是因為「事實成立」與「有機器在守」是兩件事， 而只有後者能撐過下一次重構。

02

為什麼不能共用一顆 AudioSource

pitch 是狀態，不是參數

這是整個子系統最容易被當成「過度工程」的一段，但它的根因很硬： pitch 與位置都是 AudioSource 的狀態， 不是 PlayOneShot 的參數。一顆 Source 只能有一個。

機制怎麼做為什麼這樣夠
建池依 audioSource 這顆樣板逐項複製 3D 設定 （mixer group／spatialBlend／rolloff／min-max distance／doppler／spread／priority／bypass ×3／reverb mix／custom curve）， parent 到角色 ⭐ 調 3D 設定只要改樣板那一顆，整池跟著變——不必在 Inspector 維護 N 顆一樣的 Source
租借從 _cursor 線性掃描找 _busyUntil <= Time.unscaledTime 的那一顆 環狀輪替，避免總是重用同一顆
全忙搶用 _busyUntil 最小的（＝最早會結束的＝最早借出的） 腳步是高頻短音：讓新的一步沒有聲音，比讓舊的一步播完更糟
佔用估計clipLength / max(0.01, |pitch|) 只是「什麼時候可以再借」的估計——估短了頂多提早搶用，估長了頂多多借一顆
改名遺留

池內建立的 GameObject 目前仍叫 FootstepAudioSource_0..9—— 那是 FootstepAudioSourcePool 改名時沒跟著換的字串。 只影響 Hierarchy 的可讀性，不影響行為（沒有任何程式以名稱查找它們）， 但它會讓人在 Play 時誤以為戰鬥音走的是另一個池。

03

三條播放路徑，一個池，兩套音量鏈

「調一個欄位」只對腳步成立

AudioController 對外只有三條路徑，但它們的音量鏈不一樣—— 這是這頁最容易被誤讀的一點，值得把式子寫開。

// 路徑 ① 腳步／落地 ── 經 FootstepAudioBankSO definition = bank.ResolveDefinition(Surface, Kind, landing, Gait, out volumeScale) volume = Clamp( definition.GetRandomVolume() × bank.masterVolume ← ⭐ 調整整體腳步音量只要動這一個 × volumeScale , 0, 1 ) volumeScale = landingVolume 1.10 | shuffleVolume 0（⚠️ 見 §05） | normalStepVolume 1.00 × gait{ Walk .90 | Run 1.00 | Sprint 1.05 } pitch = definition.GetRandomPitch() × { 左 0.98 | 右 1.02 } // 路徑 ② 受擊／死亡／離地 ── 經 AudioLibrarySO（O(1) 陣列查表，索引＝(int)AudioEventId） volume = definition.GetRandomVolume() ← 沒有 master，沒有類別係數 pitch = definition.GetRandomPitch() // 路徑 ③ 施法／揮擊／命中 ── 由 sink 直接指定 AudioDefinitionSO volume = definition.GetRandomVolume() ← 同 ② pitch = definition.GetRandomPitch()
⚠️ masterVolume 只作用在腳步路徑上
FootstepAudioBankSO.ApplyMasterVolume 只被 PlayFootstep 呼叫； 路徑 ② 與 ③ 直接走 PlayAt，完全不經過 Bank。 ⇒ 「要調整整體腳步音量只需要動一個欄位」這句話是對的，但「整體音量」不是—— 戰鬥與受擊音的相對響度只能逐顆 AudioDefinitionSO 的 volume 調。 📌 這不是 bug，是分層的自然結果（Bank 是腳步的配置窗口，不是全域 mixer）； 寫在這裡是為了讓下一個人不要去 Bank 裡找戰鬥音量。

分層原則

個別 clip 池的相對音量留在各自的 AudioDefinitionSO（那是音色的一部分， 例如某組素材天生較悶），跨類別的相對關係與總音量集中在 Bank。 使用者的原話是「之後要調整整體腳步聲大小，不需要去改 20 個 asset」—— 16 個腳步池的 volume 目前一律 1.0，正是這個分層生效的樣子。

洗牌袋

選 clip 不是 Random.Range，是洗牌袋：純隨機在 6 顆的池子裡， 每次都有 1/6 機率立刻重複上一顆——而「剛剛那一聲又來了」正是重複疲勞的主要來源。 洗牌袋保證每輪 N 次播放剛好用完 N 顆，並在換袋接縫處避免與前一顆相同 ⇒ 任意兩次連續播放都不同。 🐛 袋子只裝「非空」的索引——這是 2026-09-17 的修正：原本裝全部索引， 只要陣列裡有一個空引用就會隨機回傳 null、呼叫端靜默跳過 ⇒ 同一個事件時有聲時無聲（Ice_Cast 兩格裡一格失效，實際發生過）。 ⚠️ 第一版修法（保留整袋、最多重試 _bag.Length 次）是錯的： 重試途中若跨過換袋邊界就會重新洗牌，可能重複造訪同一格而漏掉有效的那一格——測試實際抓到。 ⇒ 改成由建構保證：袋裡根本沒有空格子。

04

不重新推導已 commit 的狀態

docs/16 的加重項

AudioController 讀五種上游已經決定好的東西，一個都沒有重新推導： 不比對血量、不快取上一幀的 IsDead、不看速度猜起跳、不從 MoveSpeed 反推步態、 不自己查腳下材質。讀到 true 就播一次，讀到 false 就什麼都不做。

讀什麼誰 commit 的若在這裡重新推導會怎樣守門的是
GaitPlayerLocomotionPolicy（順序 2.5） B9 平滑讓 MoveSpeed 要數十幀才爬到目標 ⇒ 整段加速期都會推錯檔位 A5 WriterRule「Gait」
SurfaceFootstepDetector（順序 6.5 步驟②） Normal／Landing 各自查 ⇒ 回到「Walk 播 Stone、收步冒出草地感」那個原始 bug 型別：三者讀同一個欄位
JustTookDamageCharacterHealth（順序 0.5） 比對血量差 ⇒ 需要自己存上一幀血量，就多了一個真相持有者 A5 WriterRule「Survivability」
JustDiedCharacterHealth（順序 0.5） 對 IsDead 做邊沿偵測 ⇒ 下游重新推導已 commit 的狀態 同上 ＋ CombatAudioTests CA1–CA6
JustLeftGroundMotionDriver（順序 6） 看垂直速度猜起跳 ⇒ 第二個回答者 A5 WriterRule「JustLeftGround」
⭐ 互斥由上游保證，所以這裡沒有防禦
致死那一幀 JustTookDamage 明確為 false—— CharacterHealth.ApplyDamage 的致死分支不抬起它（ADR-009 D2）。 因此 AudioController 不需要「死了就別播受擊」的判斷， 而那正是重點：多寫那一行不是更安全，是多了一個回答者。 ⇒ 契約由 CA1_LethalDamage_PublishesJustDied_AndNotJustTookDamage 鎖住， 不是由消費端的防禦鎖住。
誠實

JustLeftGround 是「離地」，不是「起跳」——走下平台邊緣也會抬起它。 這個近似刻意被接受，理由記在 AudioEventId.JumpTakeoff 上： ①成本是零（欄位與寫入者都已存在）；②要精確區分就得讓 JumpState 也發布一個事件， 那是為了一顆音效動 FSM。 ⛔ 若 Play 時「走下台階也有起跳聲」明顯不對，正確修法是加 Jump 自己的事件源， 不是在這裡讀速度或狀態去猜。

A25

AudioController.cs 被明確列進 A25_Slow_DoesNotLeakIntoMovementIntentConsumers 的掃描清單：它不得出現 Effect.Slow／TemporaryGameplayEffectState／ MovementSpeedMultiplier。 ⇒ Slow 只在 MovementIntent producer 上縮放，速度階層、停步、Foot IK 與音效自動沿用同一份意圖。

詞彙的兩個化石層

還在程式裡，但已經沒有人說

這個子系統演化過兩次，兩次都刻意不動 enum（因為查表以 (int) 值為索引， 只增不改不重排）。結果是程式裡留下兩層化石——讀碼的人很容易把它們當成現況。

化石還剩什麼誰取代了它證據
AudioEventId 0–3
（Landing／Left／Right／Shuffle）		 enum 值本身 FootstepAudioBankSO 全 repo 只有 Hurt／Death／JumpTakeoff 有 runtime 呼叫端； 三顆 Library 資產也只登記 4／5／6

06

為什麼 per-slot 音效不進列舉

新增法術 ＝ 掛一顆元件，程式零改動
走 AudioEventId ＋ Library走 ActionAudioSink 的欄位
適用角色層級、全域共通的事件（受擊、死亡、離地）每個 slot 各不相同的事件（火球 vs 冰刺 vs 揮劍）
新增一個改 enum ＋ 改全域查表 ＋ 改程式掛一顆元件、填兩個欄位
隱含宣告「全域只會有這幾種施法音」「這個 slot 的聲音屬於這個 slot」
先例—MeleeHitboxSink.damage ／ ThrownProjectile.slowDuration
陣營

反過來，Hurt／Death 刻意共用同一個列舉值， 沒有 EnemyHurt。玩家與敵人聽起來不同，是因為兩隻角色掛的是 不同的 AudioLibrarySO 資產（PlayerAudioLibrary ／ EnemyAudioLibrary）。 ⛔ 為敵人再開一個列舉值，等於把陣營寫進表現層的詞彙—— 而陣營在本專案是不存在的概念（CharacterHealth 的第一行註解：生存語意不分陣營）。

不節流

ActionAudioSink.Release 刻意沒有「一次執行只播一次」的閘門， 與 MeleeHitboxSink 不同。ActionState.TryAdvanceChain 會在每個連段 重置旗標並再發一次 Release（「每段各出一顆投射物」）—— 那正是我們要的：三段連擊要有三聲揮擊。 加上閘門會讓第 2、3 段無聲，而那是 chain 的正常行為不是重複觸發。 ⇒ 「一次 Action 該響幾聲」已經由 ActionState 回答完了，這裡不重複回答。 由 CA10_Sink_RepeatedRelease_IsNotThrottled 守住。

Cleanup

ActionAudioSink.Cleanup() 刻意是空的。 Cleanup 是所有結束／中斷路徑的共用收尾點，而音效是一次性的： 已經播出去的聲音不該因為 Action 被中斷而被切掉（揮到一半被打斷，揮擊聲仍應自然播完）。 需要「中斷就停聲」的是 loop 音，本輪沒有 loop 音。

EditMode

ResolveAudioController() 與 Awake 刻意分開： EditMode 的 AddComponent 不會呼叫 Awake（本 repo 踩過，commit 58b79ca）， 因此測試需要一個可直接呼叫的解析入口。沿用 MeleeHitboxSink.ResolveHitbox 已確立的寫法。 ⇒ 可測性是元件形狀的一部分，不是事後補的。
