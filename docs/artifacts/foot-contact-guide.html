Foot IK 樓梯與停步技術導讀

技術學習與實作導讀。透過 Unity 角色在樓梯移動、停步與起跑時遇到的腳部接觸問題，介紹 Foot IK 的基本原理、接觸狀態管理、骨盆補償，以及相關的診斷與驗證方法。

學習目標

閱讀本文後，應能理解：

  1. FK、IK 與腳部接觸修正之間的關係。
  2. 為什麼平地動畫在樓梯、斜坡與停步時容易出現穿透、懸空或滑步。
  3. 如何利用接觸相位、腳部鎖定與地面查詢建立 Foot IK 系統。
  4. 骨盆高度修正與雙腳可達性之間的關係。
  5. 如何區分動畫素材、角色位移與 IK 修正所造成的視覺問題。
  6. 如何使用量測、離線重播及 A/B 測試驗證修正效果。

本文中的具體數值、演算法與測試結果皆對應到實際專案版本。讀者應理解其設計依據與適用限制，而非直接將參數視為通用設定。

LAYER 0

概覽

問題：角色的腳由動畫決定，而動畫通常假設地面是平的。走上樓梯時，腳會穿進台階或懸在空中；停步時，腳可能看起來像被快速拉到落腳點。

做法：在動畫之上加一層腳部接觸系統（本專案稱為 T3）。它每幀判斷每隻腳在擺盪還是踩住：擺盪時保留動畫的抬腳高度，落地時貼上真正的踏面，踩住後把腳的水平位置鎖住。骨盆依兩腳搆得到的範圍決定身體高度。

驗證方式：每個改動都先量測。自動化探針跑上百次停步，把「動畫原本的腳」「系統算出的目標」「畫面上的腳」三條軌跡逐幀對齊比較。量測結果經常和第一印象不同——「停步時腳被吸過去」量出來不是動畫素材的問題，而是鎖腳機制造成的（5.5）。

LAYER 1

基本概念

FK 與 IK

FK：動畫給每根骨頭的角度，腳的位置是算出來的結果。IK：先指定「腳要在這裡」（IK goal），由解算器回推膝蓋與髖部。Unity Humanoid 每幀在 OnAnimatorIK 讓程式讀到 FK 的腳位置、設定目標與權重（0＝照動畫，1＝完全照目標），並調整骨盆。

為什麼樓梯特別難

  1. 角色碰撞走的不是台階。樓梯上 CharacterController 碰的是一塊平滑斜面（避免一階一階頂撞而抖動）；台階在另一個 layer，只有腳的射線查得到。root 沿斜面移動，腳卻要踩在階上——兩者每幀差 5–20 cm。
  2. 台階不連續。腳往前 1 cm 就可能跨到下一階，腳下高度瞬間跳 19.5 cm。
  3. 動畫只知道平地。停步動畫的收腳步可能只抬 8 cm，比一階還矮。

三種「地面」，最容易混淆

名稱是什麼誰用
移動面樓梯上的平滑斜面 colliderCharacterController；T3 的擺盪參考
踏面看得到的台階頂面T3 的接觸與鎖定支撐
pose 平面動畫評估當下 root 的高度判斷動畫裡這隻腳離地多高（stance）

舊版（v2，見 docs/29）每幀在腳正下方找地面、用權重把腳拉過去：擺盪腳跨階時目標跳 9–15 cm（p99），踩住的腳一滾動就跳一階，而權重不知道「這隻腳該不該在地上」。UE 的 Foot Placement、Assassin's Creed Syndicate（GDC 2016）、Johansen 2009 的共同做法是：擺盪沿連續參考面、落腳交給真實接觸面、踩住就鎖。這就是 T3。

LAYER 4

骨盆高度

腳只能伸到腿長那麼遠。兩腳在不同階時，骨盆必須降低，否則高的那隻腳搆不到。MovingPelvisSolver 用一個模型同時處理移動、停步、站立：

每隻腳提供上限
  踩住的腳   U = LegBound(下一幀髖位置, 腳目標, 腿長)
  落地中的腳 U = LegBound(...) + κ × 腳離地高度
目標  g = clamp( min(動畫想要的高度, 所有上限), −0.35 m, 0 )
步進  往下快（ω 12，跟上約束）、往上慢（決定每步起伏）
硬上限 1.05 × 腿長

為什麼往下快、往上慢：可達需求在每一步內變化約 20 cm。對稱的求解器每步都會回到原高度再降下，身體每步起伏 20–25 cm；往上的速度就是「允許的步伐起伏」預算。

為什麼要量最終骨骼：PelvisOffsetY 只是修正量，動畫本身就有 6.5–11.6 cm／步的起伏。改量最終骨骼後，診斷結論從「骨盆太平穩」翻成「整體下蹲、Walk 上樓過顛」。

LAYER 5

七項技術

每一項都依同一格式：問題 → 量測 → 做法 → 結果 → 取捨。

5.1 落腳踏面解析（LandingSurfaceResolver）

問題
擺盪參考追著「腳目前在哪一階」，跨階時在鎖定前 1–4 幀才切，單幀跳 8–17 cm。
量測
208 次停步；停步預測（ADR-010 next plant）早 7–23 幀就指向最終那一階。
做法
擺盪中（只在 Unlocked）讀下一個預定落點，接近時把參考面提前移到目的踏面；首次承諾連續 2 幀、改答案 3 幀，最後 3 幀以即時踏面驗證。
結果
上樓跨階跳動 Run 17 → 6 cm、Walk 19 → 9 cm；下樓不變（幾何限制）。
取捨
只有停步時有可信落點；即時驗證只能驗證、不能自己產生意圖。

5.2 擺盪腳長參考

問題
上樓時腳尖或腳跟先伸進下一階的立面，整隻腳被一幀抬起。
否決
把「鎖定中的立面侵入規則」擴到擺盪：一開始就 4–9 cm 深，腳鎖到錯的階、骨盆跳 13.7 cm。
做法
參考面取腳跟／腳踝／腳尖三點下方移動面的最高者。
結果
416 次停步 A/B：Walk 上樓單幀 ≥ 8 cm 的瞬拉次數，停步 175 → 71、移動中 177 → 79。

5.3 統一骨盆求解器

見 Layer 4。重點是一個模型處理移動、停步、站立，而不是三套規則各自決定高度。

5.4 Plant-aware 外插（P8b）

問題
煞車步急停時，一幀外插會過衝 5–10 cm，有時推到別階，下一幀再拉回。
量測
in-engine 反事實：同一條支撐規則，比較外插比例 k ∈ {0, .25, .5, .75, 1} 與九種策略。只有停步預測看得到「下一幀會急停」。
做法
這隻腳是下一個預定落點且在 1.5 步內 ⇒ 不外插；其餘依腳速衰減。
結果
錯階暫態 15 → 2，鎖定當幀的晚修正 max 5.3 → 2.0 cm。
取捨
落地前幾幀畫面腳加速度中位 +2.8 cm。

5.5 主案例：收步的「吸附感」

這一節示範完整的研究流程。症狀：停步時，腳像被快速拉到最後的落腳點。

三個互斥假設：H1 停步動畫本身把收腳壓縮在最後幾幀；H2 T3 提早鎖定或修正造成；H3 兩者都有。

量測設計：三條軌跡逐幀對齊——動畫腳（補上 root 位移）、T3 目標（上一幀目標＋本幀 root 位移）、畫面腳（最終骨骼）。動畫腳又用三種方式互相驗證：離線純 clip 取樣、runtime pose、runtime 把 IK 輸出歸零的反事實。IK 開啟時「畫面腳 − 套用的目標」中位 0.000 cm，才開始看數字。

Run loop（正常跑步）22–35 cm7–10 m/s
停步的最後一步6–10 cm0.8–2.7 m/s

5.6 起跑入場相位對齊（ADR-011）

問題
靜止後起跑，支撐腳貼地拖行 20–34 cm。
原因
Idle 與 Run 共用一個混合樹；Run 子動畫從它當時剛好在的相位開始，常常是錯的腳在地上。
做法
起跑那一幀把 Run 子狀態對齊到 loop 的左腳著地相位——由烘焙的腳相曲線算出（φ≈0.91），不是手填。Core 只說「下一個循環從這個相位開始」，不知道混合樹細節。
結果
動畫腳貼地滑動 20–34 → 9–10 cm。剩下約 12 cm 是 root 從 0 加速、loop 姿勢卻假設全速；接受為動畫限制，不讓 T3 藏起來。
為何 ADR
Core 第一次主動要求 Animation 改變子狀態播放相位，是新的跨層契約。

5.7 失地確認的決定性

現象
同一個測試連跑兩次，角色從樓梯頂跑出去後，進入 Falling 動畫的幀數差 1。
定位
root 軌跡與下落速度兩次完全相同，只有狀態切換差一幀——是計時，不是物理。
根因
0.1 s 與 0.35 s 的 grace 用 Time.time 絕對時刻相減。1/60 步長下 0.1 s 剛好 6 幀，float32 誤差讓「6 幀是否 ≥ 0.1」取決於 Time.time 已經多大（43–61% 的起點 6 幀就通過）。
做法
從 0 累積每 tick 的 dt，以 Time.frameCount 確保同幀只累積一次；門檻仍是時間，不綁死 60 Hz。
證明
先寫測試在舊程式上重現（8 個 case 紅），修完全綠；連跑兩次 36 個樓梯探針，gameplay 輸出 36／36 相同。

LAYER 6

方法論

先量再改，不預設答案

每一輪的開場：寫下互斥的假設，設計能區分它們的量測，量完才決定改哪一層。

區分問題來源：動畫素材、角色位移、IK 修正

「腳的動作不自然」可能來自三個不同的層，修法完全不同。做法是把它們拆成可以分別量測的軌跡：

來源怎麼單獨看到它本專案的例子
動畫素材本身離線對 clip 取樣（沒有混合、沒有 IK）5.5：停步 clip 的收腳不快；5.6：loop 姿勢假設 root 已全速
角色位移與動畫混合runtime pose 加上 root 位移；把 IK 輸出歸零的反事實；root 是否與 Bake 位移一致5.6：起跑時混合樹從錯的相位開始；5.7：root 相同、只有狀態計時不同
IK 修正畫面腳 − 動畫腳（同一座標空間、同一時間基準）5.5：鎖住時差距累積、釋放時補回

先確認動畫腳本身有沒有問題，再看畫面腳與動畫腳的差異是否由 IK 造成。只有前者正常、後者有差，才是 IK 層的問題。

時間基準與座標空間先驗證

量錯，後面所有比較都失去意義。這個專案踩過：在協程裡讀骨骼得到的是上一幀；root 在 IK 之後才移動；IK goal 與骨骼差 6 cm。做法是先跑一致性驗證（例如畫面腳 − 目標應為 0），通過才看數字。

離線重播 → runtime A/B → 人工 Play

階段成本用途
離線重播秒級，可跑十九個候選篩掉明顯不行的；前提是重播與 runtime 一致
runtime A/B分鐘級驗證重播沒模擬到的部分（例如樓梯垂直）
人工 Play人的時間「自然不自然」只有人能判斷，只留給這件事

離線模型會漂移：另一輪自己重寫的規則只有 204／247 一致，改成反射呼叫原始程式才 247／247。

分層比較

探針自己的反事實射線有差，但 IK 輸出與 locomotion 狀態完全相同 ⇒ 不是 runtime regression。

治理

只有跨系統契約改變才開 ADR；ADR 先是 Trial（可依實作修訂），驗證通過才 Accepted（凍結）。每個實驗都是預設關閉的開關，關閉時與舊版逐位元相同，還原只要把開關設回 false。

動畫資產的升級順序

資料與 runtime 參數 → 混合與播放速度 → 換 clip → 最後才改 clip 內容。5.5 的量測顯示 clip 本身不快、播放速度與 loop 相同，所以沒有理由動資產。
