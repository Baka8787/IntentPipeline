01

五個概念，別把它們混成一個

混了就會長出特例
概念是什麼誰擁有⚠️ 常見誤解
Slot 身分ActionSlot enum，數值就是身分Core/Actions❌ 不是「哪顆按鍵」。按鍵→slot 的映射住在管線順序 2
Definition 內容段落、動畫鍵、冷卻、中斷、targeting資產❌ 不是 state。一顆 state 承載多份 Definition
Phase 段落Start／Loop／End／CancelActionState❌ 連段不是新的 phase，是「Start 換素材重播」
Release 生效時點段落播到 ReleaseNormalizedTime 的那一瞬間ActionState❌ 不是動畫事件、不是粒子碰撞
Commitment 方向承諾facing：段落邊界取得一次；效果落點：前搖每帧重解、release 當帧鎖定（2026-10-12 ADR-007 D5 修訂）ActionReleaseContext❌ 不是每幀重算的瞄準
🔴 為什麼「一顆 state 承載多份 Definition」
如果每個技能一顆 state：StateType 會隨內容成長（而它是架構不變量）， 而且「能不能出手」會有 N 個回答者。
ADR-004 D2：能不能出手只由 ActionState.CanEnter 回答，不得有第二個 gate。
ADR-005 D1：身分只有一把鍵（ActionSlot）——輸入映射／冷卻／external request／ Action↔Action 中斷全部用它，不得有第二把。

FireballDefinition 實測
// FireballDefinition 展開 Phases[0] Key=Spell_Fireball_1 FallbackDuration=1.2000 Release=0.35 Interruptible=1 EmitsRelease=1 ChainSegments[0] Key=Spell_Fireball_2 FallbackDuration=1.2000 Release=0.35 ChainSegments[1] Key=Spell_Fireball_3 FallbackDuration=1.6000 Release=0.35 ChainInputOpenNormalized = 0.25 Cooldown = 0.4（整條連段共用一次） RequiresGrounded = 1 CancelMoveIntentThreshold = 0.1 Targeting = CameraConeSoftTarget
時序保證

不需要防「進場那一幀的按鍵被誤判成連按」。理由是時序： IntentData 的 trigger 旗標當幀生、當幀死（順序 7 復位）， 而 FullBodyStateMachine.Tick 是先 OnTick 才 OnEnter ⇒ 新進入的 state 第一次 OnTick 已經是下一幀，進場那次按壓早被清掉了。

03

段落轉移規則

秒數住在資產，不在程式
目前 phase條件下一步
Start時間到 且 _chainQueued換下一段 ChainSegments，phase 仍是 Start
Start時間到，沒排到連段EnterAfterStart()（Loop → End → 結束）
LoopDesiredSpeedNormalized ≥ CancelMoveIntentThresholdCancel
LoopWaitForTrigger 且同一個 slot 再次被請求End
End / Cancel時間到Complete() → Cleanup() → CommitCooldown()
收束

Cleanup() 在 OnExit 觸發，所有路徑共用—— 完成、取消、被中斷都走同一條。這是「不能留下殘態」的結構保證， 而不是「記得在每個分支都呼叫一次」的紀律。

05

Failure case ②：「受擊」借住在 Action 裡

沒有可見的 bug

這個 failure case 特別值得學，因為它沒有症狀—— 沒有閃爍、沒有卡住、沒有錯誤訊息。唯一的證據是程式裡出現了兩處長得很像的特例。

可推廣

「出手」是主動、有冷卻、有方向承諾、由自己發起； 「受擊」是被動、沒有冷卻、方向由攻擊者決定、由外部提交。 兩者共用一顆 state 時，每一條差異都會變成一個 if (slot == Reaction)。 數這種 if 的個數，就是在量這個概念被放錯位置的程度。
