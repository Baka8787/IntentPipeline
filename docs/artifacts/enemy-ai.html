兩個 seam，零個專屬步驟

順序 3 之後完全共用

cross-system-contract 說「IInputSource 可缺席 ＝ AI 角色」—— 但那只說了一半。敵人其實有一個 IInputSource， 它只是不讀鍵盤。真正的關鍵是兩個 seam 之後，管線一個字都不知道自己在跑誰。

02

三個層次不得混為一談

2026-09-10 使用者裁決

這是本子系統最重要的一節。三件事聽起來都像「敵人現在在幹嘛」， 但它們回答不同的問題、由不同的東西決定、失效時後果也不同。

🔄 敵人後來還是有了獨立的 combat context source——但 target 仍只有一份
2026-09-10 的理由是「另建 context source 只會複製 target reference ⇒ 第二份真相」。 2026-10-12 拆分（目標存活與受擊激怒是與移動無關的判定，正是原裁決自訂的重拆條件）， 但沒有複製 target：序列化的 target 仍只在 AIMovementSource， AICombatContextSource 與 AIInputSource 讀它的唯讀屬性 Target（參照資料依賴，不互相呼叫決策邏輯）。 AIInputSource 原本那份第二個 target 也一併移除。
ADR-007 D3 補充條款「⛔ 第二份 target 清單」因此仍然成立（AICombatContextSourceTests.AB1 守）。
03

EngagementMovement：五個模式與遲滯

元件私有，不進黑板
模式什麼時候輸出推進遲滯？
Approach距離 > 近戰帶上緣朝目標移動，speed = 1✅
Strafe在近戰帶內（帶內的正常解）橫向移動，speed = 0.35；換向間隔 基準 2.5 s × 隨機 0.75–1.25（實際 1.875–3.125 s）✅
Retreat距離 < 近戰帶下緣後退拉開✅
Hold零移動 fallback：未交戰／無 target／死亡直接 return，不產生任何位移—
Recoveragent 離開 NavMesh往回得去的方向走（speed 0.5）⛔ 刻意不推進
A16 邊界

A16 是三條 token 斷言：原始碼含 updatePosition = false、 含 updateRotation = false、不含 CharacterController。
⚠️ 它不會阻止同檔稍後又出現 updatePosition = true、 NavMeshAgent.Warp() 或其他直接位置寫入。 現行實作確實遵守這條紀律，但測試的保障範圍比紀律本身窄—— 這與 cross-system-contract 講的「token 掃描的已知精度」是同一件事。

🔴 Recover 是為了修一個「沒有出口的終態」
舊版離網時直接 Hold; return;——而全 repo 沒有任何一行會把 agent 放回可導航區 （isOnNavMesh 全專案只有 AIMovementSource 這一個檔案讀）。
⇒ Hold 變成一個沒有出口的終態，敵人永久靜止。 2026-09-15 錄影：連續 11 秒零位移，期間玩家跑遠也不追。
形狀：守衛本身正確地 early-return 了，錯的是 沒有任何一條路徑負責把狀態帶回可用區—— 「防呆擋住之後沒有人負責放行」。
⚠️ 這不對應 failure-atlas 現有的八類（F6 講的是「閘門擋不住某條路徑」， 這裡相反：閘門有效，但缺少回復路徑）。刻意不硬套分類。
為什麼不推進遲滯

Recover 刻意不推進遲滯狀態機，維持原設計的意圖： 離網期間的距離變化不得污染遲滯記憶。 它只回答一個問題：往哪走才回得去。
若讓它照常推進，回到 NavMesh 的那一幀就會拿到一個 「沒有任何一幀推導過的模式」——因為那段期間的距離是在無效導航下量的。

死亡

屍體不產生移動意圖。DeathState 是吸收態、確實不會走路， 所以這條在畫面上看不出差別——但決策層繼續每幀解 Approach／Strafe／NavMesh 查詢是 沒有讀者的計算，而且會讓 gizmo 報告一個屍體「正在側移」。
與 CharacterFacingSource 的死亡否決層同一個模式： 死亡由各自的消費者明確收手，不靠下游剛好擋住。

跨幀狀態：六項

全部在元件內
跨幀的東西持有者為什麼需要弄丟會怎樣
_engagementMovementAIMovementSource距離帶遲滯的記憶在帶邊緣進退抖動
_strafeDirectionSignAIMovementSource現在往左還是往右繞每幀換向 ⇒ 原地抽搐
_nextStrafeDirectionFlipTimeAIMovementSource下一次換向的時刻（基準 2.5 s × 0.75–1.25 隨機）換向時機失控
_strafeBlockedAIMovementSource⚠️ 純診斷——兩側都不可走而停步的快照，不參與任何決策（gizmo 只讀）只影響 debug 顯示，不影響行為
_memory（InCombat／受擊／寬限起點）AICombatContextSource交戰遲滯＋「這次交戰被打過沒」＋寬限計時受擊後 12 m 就放手；寬限失效
_wasWithinAttackRangeAIInputSource進入攻擊距離的邊沿每幀重複請求出手
_nextAttackRequestTimeAIInputSource0.5 s 重試間隔被拒絕後瘋狂重送
分工

注意兩個元件的跨幀狀態沒有重疊： AIInputSource 只記「該不該出手」，AICombatContextSource 只記「還在不在交戰」， AIMovementSource 只記「該怎麼移動」。三者讀同一個 target（AIMovementSource.Target）， 但不呼叫彼此的決策邏輯；移動只經黑板讀交戰結果。
