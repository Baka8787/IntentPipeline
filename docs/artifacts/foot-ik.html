01 / 問題單點採樣的資訊量天花板

最初的 Foot IK 只做一件事：從腳踝正下方打一條 ray，找到地面，把腳放上去、轉成貼合法線。這在平地與均勻斜坡上完全夠用。

它在階梯上壞掉。ray 只知道腳踝下方那一格踏面的高度，而腳掌前段有 15–25 cm 會跨進上一階的體積——系統無從得知。這不是參數沒調好，是輸入資訊量不足：一個點無法描述一個平面對另一個平面的關係。

升級的方向因此不是「加權重補丁」，而是增加採樣點，並且把「腳是一塊有長度的剛體」這件事真正放進計算裡。

02 / 架構兩條單向管道，各有唯一寫入者

Foot IK 橫跨 Unity 的兩個回呼時機，因此被拆成兩個元件。它們之間沒有方法呼叫，只有兩條方向相反的共享資料。

為什麼不直接讀骨骼

因為骨骼 Transform 在 LateUpdate 時已經被上一幀的 IK 改寫過，直接採樣會形成回饋迴路（實測症狀＝腳踝抽搐）。OnAnimatorIK 開頭抓的 GetIKPosition/GetIKRotation 才是「混合後動畫姿勢」的唯一無污染來源。

03 / 時序每幀呼叫鍊與那一幀延遲

Unity 的執行順序是 Update → Animator 評估（含 OnAnimatorIK）→ LateUpdate。Controller 在 LateUpdate 算出的目標，要到下一幀的 OnAnimatorIK 才被套用。

Tick 內部的順序

FootIKController.Tick(data)
├─ 守衛：_poseData.IsWarm？（Rig 還沒寫過就不消費全零快照）
├─ rootY   = transform.position.y          // Root 原點＝膠囊底＝地面基準
├─ ikAllowed = data.IsGrounded && !data.Arbitration.BlockIK
│
├─ ① SampleGround(left)  ─┐  每腳 3 條 ray
├─ ① SampleGround(right) ─┘
│
├─ ② ComputePelvisOffset(左 GroundY, 右 GroundY, rootY, MaxPelvisOffset)
│     └─ MoveTowards 平滑 → TargetData.PelvisOffsetY
│
└─ ③ ResolveFoot(left) / ResolveFoot(right)
      ├─ targetPosition = sample.TargetPosition
      ├─ targetRotation = sample.TargetRotation
      ├─ goalWeight     = ComputeFootWeight(腳離 Root 高度, min, max)
      └─ MoveTowards 平滑 → 位置權重／旋轉權重

SampleGround 內部

SampleGround(posePosition, poseRotation, footBottomHeight, ikAllowed)
│
├─ SampleSingleGround(posePosition)              ← 腳踝 ray（第 1 條）
│   ├─ hit.point / hit.normal
│   ├─ SoleNormal     = ClampGroundNormal(hit.normal, MaxFootAlignAngle)
│   ├─ TargetPosition = ComputeAnkleTarget(origin, hit.point, SoleNormal, fbh)   ← 泰勒斯
│   ├─ TargetRotation = FromToRotation(up, SoleNormal) * poseRotation
│   └─ GroundY
│
├─ if (!HasHit || !UseTwoPointSampling) return   ← 退化＝單點行為
│
├─ localHeel = forward * -HeelOffset - up * fbh   ← 腳自身座標系的端點
├─ localToe  = forward *  ToeOffset  - up * fbh
├─ worldHeel = TargetPosition + TargetRotation * localHeel   ← 由最終旋轉推出
├─ worldToe  = TargetPosition + TargetRotation * localToe
│
├─ heel ray（第 2 條）／ toe ray（第 3 條）  ← 從真實端點正上方打
├─ if (任一落空) return                      ← 退回 ankle-only，不關 IK
│
├─ lift = Max(0, Max(heelGroundY - worldHeel.y, toeGroundY - worldToe.y))
├─ TargetPosition.y += lift                  ← 只抬不壓
└─ GroundY = 穿透較深那一端下方的實際地面高度

04 / 幾何三層約束，各自決定不同自由度

整個求解可以拆成三層。看懂這張表，就看懂了這個子系統的全部。

層決定什麼由什麼決定
旋轉 腳的姿態（3 DOF） R = FromToRotation(up, SoleNormal) · poseRotation。左乘世界旋轉 ⇒ 動畫自身的 pitch 原樣保留（toe-up／toe-down 都不被壓平）
水平位置 腳踝 XZ（2 DOF） 等式約束：泰勒斯修正使腳踝維持在動畫 goal 的那條垂直線上
垂直位置 腳踝 Y（1 DOF） 不等式約束（只抬不壓）：lift = Max(0, Max(各端點穿透量))。argmax 的端點即接觸點，其餘自動獲得淨空

泰勒斯修正：為什麼不能沿法線偏移

直覺寫法是「命中點 ＋ 法線 × 腳底高」。在斜坡上法線不是垂直的，這一步會把腳踝水平推開——30° 坡、腳底高 0.1 m 時漂移 5 cm，而且腳還坐得太低。

踝角夾限與殘差抬升

腳底不強制整面貼地。ClampGroundNormal 把「世界 up 轉向地面法線」的量限制在 MaxFootAlignAngle 以內；超過的部分不轉，改由殘差抬升處理。結果就是上坡端接觸、下坡端自然淨空——真人在坡上正是這樣。

與 production 引擎同構

Unreal 的 ground orientation 同樣不是 100% 貼地，並且備有 heel adjustment／heel lift 類設定。換句話說：腳跟浮起是可調特性，不是缺陷；0 clearance 從來不是唯一正解。把夾限一路推高去追 0 浮空，終點是整片腳底吸附在坡面上。

05 / 參數FootIKSettings 全欄位

全部集中在一個 [Serializable] 容器裡，嵌在 Controller 的 Inspector。純資料，不含邏輯。

欄位現值意義與調整指引
GroundLayers~0地面偵測遮罩。務必包含地形所在 Layer——留 Nothing 會讓所有 ray 落空、IK 權重恆 0，症狀是「IK 好像沒作用」。
RaycastUpOffset0.5ray 起點在取樣點上方多高。需大於單步抬升與台階落差。太大會讓腳貼近立面時誤中上一階（「憑空踩半階」）。
RaycastDistance1.1ray 總長。至少涵蓋 RaycastUpOffset ＋ 預期最大向下落差。
HeelOffset0.10腳自身座標系中腳踝到腳跟後緣的距離。⚠️ 這是幾何常數，不是手感旋鈕——它定義接觸候選集合，填錯＝約束集合不完整，任何調參都救不了。現值尚未正式量測。
ToeOffset0.15同上，量到蹠球而非腳尖尖端。⚠️ 多數人形網格的腳尖上翹，量到尖端會高估 ⇒ residual 過度抬升 ⇒ 腳浮起。誤差量級 ≈ Δ × sin(該腳 pitch)，所以 pitch 大的後腳症狀最明顯。
UseTwoPointSamplingtrueA/B 開關。關閉＝只用腳踝 ray（失去防穿模殘差，但泰勒斯幾何仍生效）。僅供展示對照與退回基線，不得當成執行期的品質開關。
MaxFootAlignAngle23°腳底對齊地面法線的上限。人的背屈約 10–20°，23° 落在略寬鬆但可信的區間。視覺效果依賴 span（＝Heel＋Toe），量準端點後必須重新確認。設 180 等同無夾限。
FootGroundedHeightMin0.08動畫腳部 goal 相對 Root 平面的高度 ≤ 此值 → 權重 1（踩地相，IK 全接管）。
FootGroundedHeightMax0.25≥ 此值 → 權重 0（抬腳相，動畫全接管）。兩值之間線性過渡——刻意做成窄帶二態，腳不是全 IK 就是全動畫，避免半 IK 常態化。
WeightSmoothSpeed8權重朝目標收斂的速率（每秒）。保證不瞬切。注意它平滑的是權重，不是目標位置。
MaxPelvisOffset0.35骨盆最大下沉量。超出＝低腳搆不到，屬設計極限。骨盆只下沉、不上頂——抬升交給 CharacterController 的地面跟隨。
PelvisSmoothSpeed5骨盆偏移的收斂速率（每秒）。

可測的純函數

幾何核心全部抽成 static 純函數，不需要場景／Animator／Physics 就能在 EditMode 驗證。這是這個子系統唯一能被自動化守住的部分——視覺結果只能靠 Play。

函數回答什麼
ComputeAnkleTarget泰勒斯修正後的腳踝位置
ClampGroundNormal夾限後的腳底法線
ComputePenetrationLift兩端點的最深穿透量（只回非負）
ComputeFootWeight腳高 → 貼地權重曲線
ComputePelvisOffset雙腳高差 → 骨盆下沉（夾限、恆 ≤ 0）

06 / 迭代三次推翻，以及每次錯在哪

這一段的價值比程式本身高：每一版都「看起來合理」，都要等到 Play 才露餡。

v1 — 錯誤

雙點取「較高者」當地面高度

在連續坡面上，上坡側那個取樣點必然比腳踝正下方高，於是腳被墊起 上坡側距離 × tanθ（30° 約 8.7 cm）。更明顯的症狀是原地轉圈時腳的高度會擺動——因為誤差取決於腳朝哪。

教訓：雙點只該回答「有沒有戳穿」，不該回答「地面在哪」。

v2 — 錯誤

由 heel / toe 高差合成 pitch

連續斜面上 pitch 早就由命中法線提供（多餘）；階梯上兩點高差根本不是坡度（錯誤）——踢面 0.2 m、span 0.25 m 會合成出 39° 的假斜面，整隻腳被扳斜。

教訓：兩種地形沒有一種需要它。「新增一個資訊來源」不等於「這個來源有用」。

v3 — 錯誤

residual 用假想平面，算式裡沒有腳

穿透檢查問的是「地面有沒有戳穿一個以地面法線為法線的假想平面」。平地上這個平面貼著地面，於是永遠回 0。但真正穿地的是腳：動畫 toe-up 20° 時腳跟低於地面 2.8 cm，而 poseRotation 從頭到尾沒有進入位置解。

教訓：位置解與旋轉必須用同一個 R。當兩處各自推導同一個量，遲早會分歧。

v4 — 現行

由最終旋轉推出真實端點，點對點比較

旋轉在採樣階段算一次、存進 FootSample；端點由它推出世界座標；ray 打在真實端點正上方；穿透是點與點的高度差。動畫 pitch 因此第一次真正參與了位置解。

貫穿四版的方法論

先形式化約束模型，再改程式。前三版都是因為沒把「誰決定位置／誰決定旋轉／誰決定接觸」講清楚就動手。
改動前先算出可否證的預測——「若這個假設成立，你會看到 X cm 的偏差」。這樣 Play 才是測試，而不是觀感投票。
觀測條件 ≠ 交付條件。Scene 視窗貼著腳看到的瑕疵，在 3–4 m 的遊戲鏡頭下不存在。

07 / 邊界Level 1 的已知限制與升級階梯

接受、不修

  • 斜坡上少量 heel／sole 浮空，量級 ≈ ΔToeOffset × sin(pitch)，前後腳不對稱（後腳 pitch 大 ⇒ 誤差大）。近距離側視才可見。
  • 無 Medial／Lateral 取樣 ⇒ 側坡時腳底左右邊緣不受約束。
  • 陡下坡整個踩地相維持腳跟接觸——真人會隨步態滾向前腳掌，需要 Foot Contact／Foot Phase 與不對稱踝角上限（蹠屈 40–50° 遠大於背屈 10–20°）才能表達。
  • 階梯邊緣一端懸空；heel/toe 任一 ray 落空時退回 ankle-only（無殘差保護）。
  • IK 結果一幀延遲（架構本質）。
Level內容狀態
1Heel ＋ Toe 兩點剛體腳底近似；保留動畫 pitch；有限 slope alignment；residual 防穿；允許 heel clearance完成
2完整 foot footprint：Heel／Toe／Medial／Lateral（比照 UE 的 Foot/Floor Constraint 尺寸描述）延後
3Ball／Toe bone secondary plant——不再把整隻腳當單一剛體（比照 UE 的 BallBone）延後
重開 Foot IK 的條件（任一成立才重開）

① 平地仍固定穿模　② 斜坡有明顯懸空　③ Walk／Run／Stop 有明顯跳動　④ heel／toe ray 顯示接觸點明顯不對　⑤ 側坡出現腳底側邊明顯穿透（且該地形確實出現在展示影片中）

⚠️ 繼續調之前必須先補最小可視化（取樣點、兩條 ray、命中點與法線、最終腳底平面、lift 量）——Gizmo／Debug.DrawRay 即可，不建 Debug Framework。這一輪最大的成本就花在肉眼判讀上。
