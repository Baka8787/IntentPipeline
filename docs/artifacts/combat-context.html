戰鬥語境解剖

「現在在跟誰打、對方在哪」——這件事有七個消費者，橫跨 Core、Presentation 與 App。 這頁講的不是一個黑板欄位的欄位表，而是為什麼那七個消費者都只消費語境， 而不各自重新判斷戰鬥關係，以及那份語境的合法產生區間是怎麼被資料依賴夾出來的。

01

單一真相：七個消費者，零重新判斷

語境不是每個人自己算的

CombatContextData 只有五個欄位，但它的價值不在欄位， 在於「誰在跟誰打」這個判斷只做一次。 七個消費者各取所需，沒有任何一個重新查詢距離、角度或目標關係。

02

合法區間：順序 2 之後、敵人移動（2.5）之前

2.4 是兩種 producer 的共同落點

語境必須晚於順序 2（玩家要讀本幀剛寫好的 Intent）， 並早於它最早的消費者。2026-10-12 起，最早的消費者是敵人的移動意圖（2.5）—— AIMovementSource 讀 CombatContext 決定追不追。 ⇒ 兩種 producer 一起排在 2.4。玩家的行為不變：它的輸入在 2.4 之前都已就緒，2.4–2.6 之間也沒有任何讀者。

⭐ 互動判準已經遷移過一次（現況，非風險）
舊版用 ActionRequestTarget.PendingSlot（external mailbox）當互動判準。 受擊改走 StateType.Hurt 之後那個 mailbox 不再承載受擊—— 若不一併遷移，「被打」會安靜地停止刷新交戰計時 ⇒ 被圍毆時反而提早脫離戰鬥，且沒有任何錯誤訊息。
現行判準是兩個黑板欄位，而且涵蓋面更廣（任何來源的傷害都算互動，不再限於「記得戳 mailbox」的那些）：
interactionThisFrame = data.Intent.RequestedActionSlot != ActionSlot.None || data.Survivability.JustTookDamage;
📌 這也解釋了約束 ①：Intent 在順序 2 寫、Survivability 在順序 0.5 寫—— 兩者都必須先於本步。
03

進場、黏住、脫離

遲滯 ＋ 倒數
// 玩家（PlayerCombatContextSource，X Bot.prefab authored） enterRadius = 6 // 尚未交戰時的搜尋半徑 leaveRadius = 9 // 已在交戰時的搜尋半徑 —— 進去比出來難 disengageSeconds = 5 // 沒有互動就開始倒數 // 判準（逐字） searchRadius = wasInCombat ? leaveRadius : enterRadius inCombat = wasInCombat || interactionThisFrame || hasTarget // 敵人（AIMovementSource，Y Bot.prefab authored） aggroEnterRadius = 8 aggroLeaveRadius = 12 ⚠️ 這組門檻與 EngagementMovement 的近戰帶（1.25–1.6）是兩套獨立的東西
遲滯

搜尋半徑隨狀態切換（6 ↔ 9）就是遲滯本身——不需要額外的遲滯欄位。 進戰鬥要靠近到 6 m，脫離要拉開到 9 m 之外，中間 3 m 是不會抖動的緩衝帶。

邊界情形

「純半徑進場」沒有「上次互動」可量。程式在那一刻以進場時刻作為 disengage 計時基準—— 否則第一次走近再離開會永久卡在 InCombat（_hasInteractionTime 永遠是 false，倒數永遠不開始）。

⛔ 兩個層次不得混為一談（2026-09-10 使用者裁決）
①CombatContext＝接戰語境真相，由目標關係（黏性 enter／leave 半徑）決定， 與 NavMesh 可用性無關。
②EngagementMovement（Approach／Retreat／Hold）＝可導航前提下的移動模式。
⛔ 「NavMesh 無效」不等於「沒有 target／脫離戰鬥」——語境真相要保留。 細節見 enemy-ai.html。
04

Target ／ Soft Target ／ Interaction

三個不同的東西
概念回答什麼誰消費⚠️ 常見誤解
Target
HasTarget／TargetPosition		「我現在在跟誰打」Facing（Priority 2）、HeadLook不是 lock-on——它不鎖定，只是語境
Soft Target
HasSoftTarget／SoftTargetPosition		「這一擊該往哪」ActionState 的 targeting 解算🔴 沒有黏性——每幀重選、無記憶（程式註解：「每幀、無記憶」）。黏性只屬於 combat target。且只有顯式 CameraConeSoftTarget 的 Action 才吃
Interaction
（內部 _lastInteractionTime）		「我最近有沒有在打」只有 producer 自己（倒數基準）不進黑板——它是判準的中間量，不是語境
為什麼分開

Target 是關係（黏性、跨幀），Soft Target 是意圖（每幀、無記憶）。 「我在跟這隻打」與「這一發火球往哪飛」可以不同——例如你正在跟 A 交戰，但準心掃過 B。 合成一個欄位會讓 facing 跟著準心跑，那正是 direction-authority 要拆開的三個方向概念之一。
⚠️ 兩者的記憶特性相反，這正是它們必須是兩個欄位的理由： 把無記憶的意圖存成黏性關係，準心一掃過去角色就轉身不回來了。

05

跨幀狀態

全部在 producer 內，不在黑板
跨幀的東西持有者為什麼需要弄丟會怎樣
_lastInteractionTime
_hasInteractionTime		PlayerCombatContextSource5 秒脫戰倒數的基準永久卡在 InCombat，或一停手就立刻脫戰
_targetMarker
_targetCollider		PlayerCombatContextSource維持「同一個目標」而不是每幀重選最近的兩個敵人等距時目標每幀跳動
上一幀的 InCombat黑板（讀回自己上一幀的值）遲滯需要知道「我原本在不在戰鬥中」搜尋半徑無法切換 ⇒ 遲滯消失
零配置

候選搜尋用固定容量的 _candidateBuffer（建構期一次配置）＋ 非配置 overlap 查詢。 熱路徑只需要當幀最優候選，不保存列表，溢出的候選直接忽略—— 這與整個 repo 的零 GC 紀律一致：固定容量是刻意的，不是待優化的上限。
