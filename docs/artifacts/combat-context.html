「現在在跟誰打、對方在哪」——這件事有七個消費者，橫跨 Core、Presentation 與 App。 這頁講的不是一個黑板欄位的欄位表，而是為什麼那七個消費者都只消費語境， 而不各自重新判斷戰鬥關係，以及那份語境為什麼只能在順序 2.6 產生。

01

單一真相：七個消費者，零重新判斷

語境不是每個人自己算的

CombatContextData 只有五個欄位，但它的價值不在欄位， 在於「誰在跟誰打」這個判斷只做一次。 七個消費者各取所需，沒有任何一個重新查詢距離、角度或目標關係。

02

順序 2.6：一個只有三格寬的夾縫

玩家 producer 的時序約束

敵人的語境可以在 2.5 產生，因為它不需要看玩家的輸入。 玩家的不行——它有兩個方向的硬約束，把它夾在一個很窄的位置。

🔴 這條依賴曾經差點被切斷
docs/26 §I 記錄：受擊 seam 從 ActionRequestTarget 遷出時， docs/15 §4.1 明文把 ActionRequestTarget.PendingSlot 當成戰鬥語境的進入條件—— 離開 mailbox 必須同步遷移 PlayerCombatContextSource， 否則會出現「被圍毆時反而提早脫離戰鬥」，而且沒有任何錯誤訊息。
這是 failure-atlas F4（關係不存在）的近親：兩個子系統共用一個欄位當判準，而那個共用關係只寫在文件裡。
03

進場、黏住、脫離

遲滯 ＋ 倒數
// 玩家（PlayerCombatContextSource，X Bot.prefab authored） enterRadius = 6 // 尚未交戰時的搜尋半徑 leaveRadius = 9 // 已在交戰時的搜尋半徑 —— 進去比出來難 disengageSeconds = 5 // 沒有互動就開始倒數 // 判準（逐字） searchRadius = wasInCombat ? leaveRadius : enterRadius inCombat = wasInCombat || interactionThisFrame || hasTarget // 敵人（AIMovementSource，Y Bot.prefab authored） aggroEnterRadius = 8 aggroLeaveRadius = 12 ⚠️ 這組門檻與 EngagementMovement 的近戰帶（1.25–1.6）是兩套獨立的東西
遲滯

搜尋半徑隨狀態切換（6 ↔ 9）就是遲滯本身——不需要額外的遲滯欄位。 進戰鬥要靠近到 6 m，脫離要拉開到 9 m 之外，中間 3 m 是不會抖動的緩衝帶。

邊界情形

「純半徑進場」沒有「上次互動」可量。程式在那一刻以進場時刻作為 disengage 計時基準—— 否則第一次走近再離開會永久卡在 InCombat（_hasInteractionTime 永遠是 false，倒數永遠不開始）。

⛔ 兩個層次不得混為一談（2026-09-10 使用者裁決）
①CombatContext＝接戰語境真相，由目標關係（黏性 enter／leave 半徑）決定， 與 NavMesh 可用性無關。
②EngagementMovement（Approach／Retreat／Hold）＝可導航前提下的移動模式。
⛔ 「NavMesh 無效」不等於「沒有 target／脫離戰鬥」——語境真相要保留。 細節見 enemy-ai.html。
04

Target ／ Soft Target ／ Interaction

三個不同的東西
概念回答什麼誰消費⚠️ 常見誤解
Target
HasTarget／TargetPosition		「我現在在跟誰打」Facing（Priority 2）、HeadLook不是 lock-on——它不鎖定，只是語境
Soft Target
HasSoftTarget／SoftTargetPosition		「這一擊該往哪」ActionState 的 targeting 解算只有顯式 CameraConeSoftTarget 的 Action 才吃；預設是 CameraForward
Interaction
（內部 _lastInteractionTime）		「我最近有沒有在打」只有 producer 自己（倒數基準）不進黑板——它是判準的中間量，不是語境
為什麼分開

Target 是關係，Soft Target 是意圖。 「我在跟這隻打」與「這一發火球往哪飛」可以不同——例如你正在跟 A 交戰，但準心掃過 B。 合成一個欄位會讓 facing 跟著準心跑，那正是 direction-authority 要拆開的三個方向概念之一。

05

跨幀狀態

全部在 producer 內，不在黑板
跨幀的東西持有者為什麼需要弄丟會怎樣
_lastInteractionTime
_hasInteractionTime		PlayerCombatContextSource5 秒脫戰倒數的基準永久卡在 InCombat，或一停手就立刻脫戰
_targetMarker
_targetCollider		PlayerCombatContextSource維持「同一個目標」而不是每幀重選最近的兩個敵人等距時目標每幀跳動
上一幀的 InCombat黑板（讀回自己上一幀的值）遲滯需要知道「我原本在不在戰鬥中」搜尋半徑無法切換 ⇒ 遲滯消失
零配置

候選搜尋用固定容量的 _candidateBuffer（建構期一次配置）＋ 非配置 overlap 查詢。 這與 AimResolver 的 _hitBuffer 是同一個模式： 熱路徑只需要當幀最優候選，不保存列表，溢出的候選直接忽略。
