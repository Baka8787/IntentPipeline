Traversal 解剖

角色前面有一堵 1 公尺高的矮牆。普通跳躍表達不了「翻過去」。 這套系統每幀偷看前方幾何，判斷「那是什麼、身體過不過得去」， 在你按下跳躍的那一瞬間把答案鎖起來，播一支翻越動畫， 並把那支動畫的 root 軌跡重新映射到現場真正的邊緣位置上。
關鍵詞是 committed（已承諾）：一旦開始就不再看環境、不再吃輸入。
⚠️ 2026-09-21（ADR-008 D10）起，committed 的定義被改述過一次—— 固定的是 landmarks／timing／contact targets，不是「絕對軌跡」。 差別與它為什麼仍然算 committed，見 §06。

01

八個階段：每一層回答一個不同的問題

理解 traversal 唯一有效的骨架

把任兩層合成一個「TraversalState」方塊，你就再也無法回答 「為什麼畫面顯示 Climb1m 卻什麼都沒發生」。 每一層都有自己的 RejectReason，而失敗發生在哪一層決定了你該去改什麼。

02

四個 landmark 來自三個不同來源

最容易誤解的部分

每個 landmark 的時間與位置可能來自不同的權威—— 時間屬動畫（bake 量的），位置屬世界（probe 量的）。混用它們就會出現「手抓著牆卻在滑」這種 bug。

Landmark時間從哪來位置從哪來最終 authority
Entry 進場固定 t = 0🔵 角色當下真正站的地方🔵 Probe——entry correction 恆為 0，起點就是角色自己
L / R Hand Contact🟢 Bake🔵 Probe 的 LedgeFrame混合：時間屬動畫、位置屬世界、橫向偏移屬動畫
Transfer 重心轉移🟢 Bake⭐ 刻意沿用 Right Contact 的 correction🟢 動畫（這一段 root 不額外修正）
Exit 脫離🟢 Bake🔵 Probe 的 DestinationPoint兩者取近——再遠不保證還在已驗證的落腳面上
Recovery 恢復控制🟢 Bake 與 binding 取大同 Exit🟢 動畫

關鍵

注意這個方向：感測範圍不是 authored 常數，而是從「動畫需要站多遠」反推出來的。 這正是下一節那個 bug 的修法——讓需求從有資料的那一層推過來。

05

Failure case：站對了卻爬不上去

沒有任何一層說謊

症狀：明明對著牆、明明按了跳躍，大部分站位都不觸發； 只有很窄的一小段站位會成功。

階段觀察到什麼是不是凶手
1 ObservationforwardScanDistance 是 authored 常數 1.25 m⚠️ 記著
2 Candidate站遠一點 ⇒ ray 打不到 ⇒ NoForwardHit ⇒ Kind = None❌ 症狀，不是根因
3 EntryVault1m 由 bake 推導的理想進場距離是 1.4017 m🔴 就是這裡
為什麼這個 bug 很難看出來
因為每一層看起來都沒錯——Probe 忠實回報「我沒看到東西」； Classifier 忠實回報 NoForwardHit；Entry 根本沒被呼叫到（candidate 是 None）。
沒有任何一層說謊，錯的是兩個常數之間的關係——而那個關係在程式裡原本不存在。
可推廣

修法不是「把 1.25 改大一點」，而是讓需求從有資料的那一層推過來： CanEnter 每次都用 bake 的實際值重推 GetRequiredSensingReach() 餵給 Probe。 改資產值只治這一支動畫；把關係寫進程式才治所有動畫，也治將來換動畫的那一天。

06

第二種 execution model：Segmented

ADR-008 D10 · 2026-09-21

§01–§05 描述的是 Absolute：每幀直接求 committed plan 的絕對 pose，取前後差值當位移。 Vault1m 與 Climb1m 仍然走這條，行為未變。 Climb2m 的 binding 現在 author 成 Segmented——差別可以壓成一句話：

⭐ 一句話的差別
Absolute 問「這一幀 plan 說我該在哪」；
Segmented 問「從我現在真的在的地方出發，怎麼在下一個 committed landmark 之前把誤差收掉」。
desired(t) = plan.TryEvaluate(t) + carriedError × (1 − smoothstep(u)) carriedError = 段開始時的 actual root − plan.TryEvaluate(段開始時間) ← 整段只取樣這一次 u = (t − 段起) / (段迄 − 段起) // 段內形狀仍然是同一份 committed plan。變的只有一個衰減到零的偏移量。
invariant內容違反會怎樣
I6 🔧committed landmarks／timing／contact targets 在一次 traversal 內是常數
（2026-09-21 改述；原文是「plan 在一次 traversal 內是常數」）		root 目標抖動
I7a執行分段：每段起點取角色當下實際 root，終點是 committed landmark；段內是開迴路誤差跨段累積，最後永久偏掉
I7bplan 是絕對 pose 的函數；被碰撞擋掉的位移不回授進 plan——它只會在下一個 phase boundary 被吸收。⚠️ 最後一段沒有下一個 boundary會誤以為「plan 錯了」
I11 🆕rebase 取樣點只能是 phase boundary，而且只能讀角色自己的 transform.position。⛔ 不得讀 Physics／Probe、⛔ 不得段內重取樣committed 的語意退化成 continuous motion
I12 🆕Segmented 的 compensation 只承載執行誤差（公分級），不得承載牆高適應（公寸級）——後者屬 landmark 層補償量變大 ⇒ 抓握期間把手臂拉出 reach budget
機器化

I11 是由原始碼規則守的，不是靠紀律。 ArchitectureRegressionTests 直接掃 MotionDriver 的方法本體： TraversalExecutionSegment.TryCreate( 在整個檔案裡只能出現一次， 且必須出現在開啟 segment 的那個方法裡； 段內逐幀 evaluation 的方法本體不得出現 TryCreate 或 actualSegmentStart。 ⇒ 想在段內偷偷重取樣，測試會在原始碼層變紅。

為什麼只有 Climb2m

Climb2m 是唯一整段靠手支撐、且垂直位移接近 2 m 的動作。 Absolute 路徑下被碰撞擦掉的位移沒有任何機會補回， 實測在 1.8 m 牆殘留 12.7 cm、1.6 m 牆殘留 34.1 cm。 Vault1m 的位移短、且以水平為主，沒有觀察到同樣的累積。
⚠️ 這是實測差異，不是原則差異——哪天 Vault 也量到累積，就把它的 binding 也 author 成 Segmented。

能力空缺

coverage 有三個不同的下限，取最保守者：運動學 ≈1.58（接觸瞬間手臂打直）／ IK guard ≈1.62（contact pre-IK 殘差撞到 maximumResidualDistance 0.35）／ authored 1.65。
⇒ 1.20 – 1.65 m 這一段沒有任何 traversal 動畫（Climb1m 的 coverage 是 [1.0, 1.2]）。 落在這裡的牆由 TraversalSelectionPolicy 以 OutsideAnimationCoverage 明確否決、退回一般 Jump。 📌 這是資產限制，不是程式缺陷——寫在這裡是為了讓下次看到「這堵牆爬不上去」時， 先去對 coverage，而不是去 debug 執行層。

一幀延遲

docs/40 順帶挖出一個與 execution model 無關的缺陷： OnAnimatorIK 在 LateUpdate 之前，而 root 位移在之後才套上 ⇒ 手每幀浮在 target + Δ（60 fps 約 4.8 cm，幾乎全部朝上，就是「抓空氣」）。 補償後中點殘差 6.77 cm → 0.60 cm。
⭐ 值得記住的是它的形狀：兩個 callback 的相對順序，變成了一個看得見的視覺缺陷—— 和 authority-timeline.html 裡那些「一幀延遲」是同一類東西。
