方向權威解剖

角色身上有三個不同的方向概念：往哪走、面朝哪、這一擊打向哪。 它們長期共用兩個載體——後果是 strafe 在數學上不可表達， 而且連段時「人」與「火球」會分家。
這頁講那三個概念怎麼被拆開，以及一條可以用計算機驗算的漂亮性質：為什麼不會滑步。

02

Facing 的四段優先序與死亡否決層

只有一層吃死區
🔴 死亡是否決層，不是 Priority 0
2026-09-14 Play 回報：屍體會不斷面向玩家。 DeathArbiterSource 擋不住——它封鎖的是 BlockInput，也就是輸入產生的意圖； 但 facing 的第二順位讀的是 CombatContext，由 AIMovementSource 在順序 2.5 直接寫入黑板，根本不經過輸入 ⇒ 封鎖輸入對它毫無作用。
修法是不送 request ⇒ MotionDriver 維持既有 rotation ⇒ 這正是 Priority 4 既有的語意。⛔ 因此不需要新增任何「凍結朝向」機制。
可推廣

「封鎖輸入」只擋得住經過輸入的東西。 任何直接寫黑板的 producer（AI、網路、replay）都繞過它。 下次想用 BlockInput 關掉某個行為之前，先問那個行為的資料是不是從輸入來的。

03

驗算：為什麼不會滑步

整個 locomotion 最漂亮的一件事

滑步（腳在地上滑）的根因永遠是「腳步速度 ≠ 世界速度」。 這個專案的解法可以用計算機驗算——而且它在速度軸上每一點都成立。

⚠️ Inspector 上的 moveSpeed 是假的
X Bot.prefab 的 Inspector 顯示 moveSpeed = 5.66， 但它在 Awake 會被 Bake_SprintFwdLoop 的實測速度 覆寫成 6.2614。
所以拿 Inspector 的值去驗算上面那張表，四個節點都會對不上—— 而那不是表錯了，是你讀到的欄位在執行期不生效。
04

四層職責邊界

移動控制方案住在 Producer
層負責什麼⛔ 不負責
Producer 意圖把輸入翻成 MovementIntent；移動控制方案（相機相對／角色相對）住這裡不認識 gameplay state、不認識「封鎖」
Dynamics 動力學B9 平滑、gait 檔位、停步段選擇不決定朝向
Facing 朝向解出「該朝哪」，四段優先序 ＋ 死亡否決不自己寫 transform.rotation
Execution 執行MotionDriver 是 transform 的唯一寫入者不決定該朝哪
為什麼

「移動控制方案」住在 Producer 而不是 Facing——因為它決定的是輸入怎麼變成意圖 （推上＝往鏡頭前方，還是往角色前方），那是翻譯，不是朝向。 放錯層就會讓「改控制方案」連帶改到朝向行為。
