失效模式圖鑑

六個子系統架構頁裡的 failure case，拆開重排。依「壞法」分類，不依「哪個系統」分類—— 因為同一種壞法會在不同子系統重複出現，而你下次遇到的那次，多半在還沒寫出來的系統裡。
每一類都給三樣東西：怎麼認出它、去哪裡找、可推廣的判準。

分診：從症狀找到類別

先問，再讀

這張圖的用法是：把你看到的症狀對到最左邊那一欄，然後回答中間那個問題。 答案會把你指到某一類——那一類的「去哪裡找」通常比再讀一次程式碼有效。

F1

不連續性憑空出現

選擇型分支
判準max() 是連續的；「選出 argmax 之後改讀它的別的欄位」不是。
怎麼認

兩態之間反覆跳動，而且退化情形（平地／兩值相等）完全正常。退化時正常正是關鍵線索——那代表跳幅在退化時是 0。

去哪找

程式裡的硬分支：三元運算、if/else 選擇、OrderBy().First()。特別注意「用 A 比大小，卻回傳 B」的形狀。

實例

Foot IK 斜坡骨盆震盪：GroundY = heelPen >= toePen ? heelHit.y : toeHit.y。 兩個輸入都連續、max() 也連續，不連續是在「選了誰之後改讀它的另一個欄位」那一步憑空出現的。 跳幅 ＝ 跨距 0.195 × 坡度梯度。→ foot-ik-architecture §06

紅線

由「不連續選擇」導出的量，不得餵給被當成連續量使用的下游。（Foot IK I10）

F2

時機決定語意

同一變數，兩個意思
判準一個變數在管線的不同時點代表不同的物理量，而發布時機決定下游拿到哪一個。
怎麼認

一個功能「從來沒有觸發過」；或某個數值看起來合理但永遠是同一個值。你會很自然地以為「它本來就這樣」。

去哪找

發布點與夾持／覆寫點的相對順序。問：這個值在被發布之前，有沒有經過任何會改寫它的處理？

實例 ①

重落地永遠判不出來：VerticalVelocity 若排在 reboundForce 貼地夾持之後發布， 落地幀的撞地速度（−12）就被貼地力（−2）取代，|−2| > 8 永遠不成立。→ jump-landing §04

實例 ②

膠囊進牆：V1 的順序是 Clamp → Smooth，夾持壓小的是目標，而平滑值還停在上一幀的大值 ⇒ 寫進 center 的數字大於安全值。→ dynamic-capsule §04

實例 ③

樓梯上腳步聲的地面高度慢一幀：①②若對調，事件來源會讀到上一幀的地面觀測。

紅線

認識外界約束的那一層之後，不能再有任何會改變數值的處理。

F3

量測代理不對題

量了 A 去回答 B
判準代理量的可信區間比它的平均誤差重要。在某段相關、在另一段完全無關的代理，比一個一致偏差的代理更危險。
怎麼認

「開了看不出效果」但原本的問題還在。或是同一個機制在某些情況過度反應、在另一些情況完全不反應。

去哪找

問一句：我量的這個東西，和我想回答的問題，是同一件事嗎？兩者只要有一個情境下脫鉤，那個情境就會壞。

實例 ①

用 MoveDirection 代理身體傾斜：純側移時身體實際往反方向傾 0.029，舊模型卻往移動方向推 0.12 ⇒ 在完全沒問題的地方製造了 0.149 m 的誤差；而真正需要 0.20–0.30 的前向跑步只給 0.12。 兩端都錯，方向還相反。→ dynamic-capsule §07

實例 ②

用骨骼點代理網格：Head 骨骼在顱底，只超出膠囊 8 cm，而臉與頭頂的網格超出 27 cm ——低估 3–10 倍，於是得出「不需要 dynamic capsule」的錯誤結論。→ dynamic-capsule §06

紅線

Play 觀察與推導衝突時，先懷疑判準，不要先懷疑觀察。

F4

關係不存在

每一層都沒說謊
判準兩個常數之間應該有一個關係，而那個關係在程式裡不存在——它只存在於某個人的腦中。
怎麼認

逐層追查之後每一層看起來都正確，但合起來就是不 work。沒有任何一層在說謊。

去哪找

找那兩個「本來就該互相知道」的數字。通常一個在資產、一個在另一個資產，中間沒有任何程式把它們連起來。

實例

站對了卻爬不上去：感測範圍是 authored 常數 1.25 m，而 Vault1m 由 bake 推導的理想進場距離是 1.4017 m ——理想站位落在感測範圍之外，交集只剩 25 cm。→ traversal §05

修法

讓需求從有資料的那一層推過來，不要改大某個常數。
改常數只治這一支動畫；把關係寫進程式才治所有動畫，也治將來換動畫的那一天。

F5

Authored 值就是根因

grep 永遠找不到
判準程式完全正確地執行了一份空的／錯的資料。根因在 Inspector，不在原始碼。
怎麼認

「這個功能從來沒觸發過」，而且你已經確認程式邏輯是對的。read the code 讀十遍也不會發現。

去哪找

那個 gate 讀的是哪個 authored 欄位，然後去資產上看它的值。空清單、預設 false、未填的 enum 是三大常客。

實例 ①

敵人打不斷：EnemyPunchDefinition.Phases[0].Interruptible = 0。 Super Armor 零新程式——它是一個資產欄位。→ action-combat §04

實例 ②

空中被打完全沒反應：Jump 的 CanBeInterruptedBy 是空清單——連死亡都擋掉。→ jump-landing §05

實例 ③

ThrowDefinition 沒有 Slot 值（序列化早於該欄位存在 ⇒ 實際為 None）。目前沒被註冊所以不出事，一旦加進 config 就會綁錯。

守衛

這一類正是 PrefabWiringTests（Verification Ladder L1）存在的理由—— 接線由人做，接線對不對由測試講。

F6

閘門管不到那條路徑

關了但還在動
判準「封鎖輸入」只擋得住經過輸入的東西。任何直接寫黑板的 producer 都繞過它。
怎麼認

「我已經關掉它了，為什麼還在動」。而且你檢查過那個開關確實生效了。

去哪找

畫出那個行為的資料來源鏈，然後問：這條鏈有經過我關掉的那一環嗎？AI、網路、replay 這類 producer 通常不經過。

實例

屍體會不斷面向玩家：DeathArbiterSource 封鎖的是 BlockInput， 但 facing 的第二順位讀的是 CombatContext，由 AIMovementSource 在順序 2.5 直接寫入黑板——根本不經過輸入。 → direction-authority §02

修法

修法是不送 request，讓既有的「沒有人要求 ⇒ 維持現狀」語意接手。
⛔ 不需要新增「凍結朝向」機制——那是在既有語意之外再造一個。

F7

回授邊讓外界擁有記憶

離開後要慢慢恢復
判準平滑器該追意圖，不該追被環境修正後的結果——否則環境就偷偷變成了狀態的第二個擁有者。
怎麼認

離開某個情境之後，行為要慢慢恢復，而那個延遲沒有任何設計理由。或是出現抽搐／自激震盪。

去哪找

找回授邊：有沒有一條線把「輸出」或「被修正後的結果」接回「狀態」。畫成圖之後它會很明顯。

實例 ①

離開牆邊後偏移要重新長回來：若把碰撞夾持的結果餵回平滑器，貼牆時平滑值被壓到接近 0， 牆消失後還要慢慢恢復。現行作法讓平滑器追 CappedOffset，牆消失的那一幀就恢復完整偏移。→ dynamic-capsule §03

實例 ②

腳踝抽搐／腳黏地：OnAnimatorIK 若先套用再拍快照，快照就拍到自己剛套上去的 IK 結果 ⇒ output → input 迴路。→ foot-ik-architecture §04

紅線

決策端的輸入永不來自自己輸出的結果。（Foot IK I1）

F8

同一句話出現第二次

沒有症狀
判準同一句話在程式裡出現第二次時，它就不再是特例，而是一個被放錯位置的概念。
怎麼認

沒有症狀。沒有閃爍、沒有卡住、沒有錯誤訊息。唯一的證據是兩個看起來無關的地方有同一個 if (x == Special)， 而且它們的註解在說同一句話。

去哪找

數特例。數這種 if 的個數，就是在量這個概念被放錯位置的程度。

實例

「受擊」借住在 Action 裡：ShouldFaceTargetOnEnter 有 && slot != Reaction （註解：「受擊不是出手，被打的人不該自己轉去面對攻擊者」）；AllowsSameSlotReentry 只允許 Reaction 自我重入 （註解：「硬直中再被打要再踉蹌一次」）。程式自己說了兩次「受擊不是出手」。→ action-combat §05

紅線

正確的結論不是加第三個例外，而是把那個概念搬出去。
