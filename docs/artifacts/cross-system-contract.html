跨系統契約

子系統之間不互相引用。它們只共用三樣東西：一塊黑板、一組驅動介面、一條管線順序。 這頁講的是那三樣東西的規則——每個子系統都必須遵守， 而違反它們的症狀通常出現在別的子系統裡。

01

黑板：七個區，七個唯一寫入者

A5 守著

黑板不是「大家都能寫的全域變數」。每一區都綁死在一個管線順序上， 所以「這個值什麼時候變」永遠有答案——這是整個架構可推理性的來源。

敵人在 2.5 寫、玩家在 2.6 寫——但同一個角色只會有其中一個。 這是「每個 actor 一個寫入者」，不是「一個欄位兩個寫入者」。
玩家為什麼非得在 2.6：它要讀順序 2 剛寫好的 Action intent，又必須在順序 4 之前 （external ActionRequestTarget 會被順序 4 評估後清除）——那個夾縫就是 2.6 存在的理由。
02

三種 intent 語意：復位規則完全不同

最容易混用的一節

它們都叫「意圖」，但復位方式三者互斥。 把其中一種的規則套到另一種身上，就是這個專案踩過最貴的幾個坑。

語意怎麼復位「跳過寫入」等於什麼誤用的症狀
trigger 邊沿順序 7 明確清空該幀沒有意圖 ✓忘了清 ⇒ 意圖殘留，連按一次變兩次
連續型⛔ 不復位🔴 凍結在最後一幀（≠ 歸零）封鎖時角色全速前進放不下來
廣播快照整體覆寫即復位沿用上一幀的快照消費者「讀完就清」⇒ 兩個消費者互相吃掉事件
判準

要判斷一個新欄位屬於哪一種，問：「沒有人寫它的那一幀，它應該是什麼？」
應該是「沒有」⇒ trigger 邊沿。應該是「上次那個值」⇒ 連續型。 應該是「沒有人再關心」⇒ 廣播快照。

03

驅動介面：Runner 不認識什麼

DIP 的實際形狀

每個介面存在的理由都可以寫成同一句話：「讓 Runner 不需要認識 X」。 下表第三欄就是那個 X——那才是介面真正的價值，不是「多一層抽象」。

介面順序讓 Runner 不必認識缺席時
IInputSource1裝置、按鍵、Input System✅ 以 default InputData 跑完整管線（＝AI 角色）
IMovementIntentSource2.5移動策略（Shift=Sprint 這類規則）❌ MovementIntent 恆 0，角色不動
IMovementModel3平滑、MoveSpeed、gait❌ 無運動輸出，也進不了 Move 狀態
IArbiterSource4.5具體封鎖語意（UI／死亡／暫停）✅ 沒有人要求封鎖 ⇒ 全 false
CharacterHealth0.5傷害、受擊、死亡動畫✅ 整段跳過
TraversalProbe2.7幾何量測與分類✅ 整段跳過，Traversal gate 恆 false
IPresentationController6.5①IK／音效／特效的具體實作✅ 沒有表現輸出
IPresentationEventSource6.5②事件如何被偵測✅ 事件區恆為 default
IActionLifecycleSink—世界效果（開命中窗／生投射物）⚠️ 動畫照播，但沒有任何世界效果
「可缺席」是一個設計，不是防禦性程式
IInputSource 缺席不是錯誤——那正是敵人角色的定義： 沒有輸入源，由順序 2.5 的 producer 直接產生 domain intent。 玩家與敵人共用順序 3 之後的整條管線，差別只在第一格由誰填。
⚠️ 相對地，IMovementIntentSource／IMovementModel 缺席是真的壞掉， Runner 在 Awake 會 LogError——但那要等到 Play 才看得到， 所以 PrefabWiringTests 在 EditMode 先擋一層。
